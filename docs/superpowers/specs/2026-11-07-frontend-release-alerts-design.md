# Фронтовые алерты: упоминания и состав задач

Дата: 2026-11-07. Небольшая доработка `services/webhook-alerts` в репозитории `.github`.
Статус: подтверждён пользователем 2026-11-07.

## Цель

По сообщению об очереди должно быть видно, какая задача готовится к выпуску.
Инициатор действия должен получать Telegram-упоминание. Результаты выкатки
должны содержать полезный итог без отмеченных пользователем технических подробностей.

## Согласованное поведение

- В сообщении «PR #N поставлен в очередь» упоминаем человека, поставившего PR
  в очередь (`mergeQueueEntry.enqueuer`), а не автора PR.
- Добавляем названия связанных задач со ссылками, аналогично результатам выкатки.
  Источник — `closingIssuesReferences` конкретного PR. Если задач нет,
  показываем название PR со ссылкой на него. Кнопка «Открыть PR» остаётся.
- В результатах успешной и неуспешной выкатки после «Запустил» упоминаем
  инициатора запуска, сохраняя существующий выбор `run.actor`.
- Удаляем из этих результатов пояснение «Слева — последний подтверждённый выпуск…»,
  строку с полным SHA релиза и строку с digest образа BFF.
- Сохраняем короткую строку «Версия», список задач, Health Check, сведения
  об этапе сбоя и состоянии выкатки, а также существующие кнопки.

## Подходы

1. **Выбран пользователем:** доработать текущий механизм упоминаний по Telegram ID
   и существующий способ получения задач. Проверить действующую карту
   `TELEGRAM_USER_MAP` на проде и исправить подтверждённую причину отсутствия пингов.
   Это использует уже имеющиеся данные и общий форматтер `mention`.
2. Перейти на Telegram `@username`. Вынесен пользователем в отдельную задачу
   [#62](https://github.com/Cringe-Driven-Development-Team/.github/issues/62)
   в Backlog: в текущей доработке используется существующий механизм по ID.

## Ограничения и границы

Новые зависимости и отдельный справочник пользователей не нужны. Не меняем
выбор получателя на автора PR или исполнителя задачи. Не переделываем уведомления
о публикации артефактов, начале выкатки и откате; общая правка упоминаний может
исправить пинги и в них. Не редактируем старые сообщения.

Сохраняем экранирование HTML, ограничение длины сообщений, дедупликацию,
проверку актуальности очереди перед отправкой и существующие повторные попытки.
Не раскрываем токены и содержимое секретных настроек в логах или документации.

## Решения для реализации

Причина отсутствия упоминаний ещё не установлена: код уже вызывает `mention`,
а `main.ts` передаёт карту пользователей в обработчик релизов. Нужно проверить
реальную конфигурацию и путь её доставки в сервис, затем исправить источник
проблемы. Проверенные Telegram ID переиспользуем из существующей карты.

Предложение агента для граничных случаев: неизвестный аккаунт остаётся обычным
GitHub-ником; сбой получения задач не выдаём за отсутствие связанных задач.
Детали повторного использования запроса задач и обработки сбоя уточняются в плане
по существующему поведению API и очереди. Новую рассылку для проверки не вводим.

## Проверка результата

- Тесты сообщений подтверждают упоминание именно инициаторов действий
  при отличающемся авторе PR и корректной карте пользователей.
- Проверены одна и несколько связанных задач, отсутствие задач, сбой API,
  экранирование названий и ограничение длины сообщения об очереди.
- В успешном и неуспешном результате отсутствуют три удаляемых блока;
  задачи, короткая версия, диагностика и кнопки сохранены.
- Тесты сервиса и проверка типов проходят; повторные попытки и защита
  от отправки устаревшего сообщения об очереди сохраняются.
- На проде отдельно проверяется применённая карта и корректность формирования
  упоминаний. Проверку реального уведомления фиксируем по следующему штатному
  событию; до неё не утверждаем, что доставка пинга проверена в Telegram.
