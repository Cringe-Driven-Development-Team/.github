# Разработка фронта и бэка в организации команды

Дата: 2026-10-17

Статус: черновик для ревью пользователя. Согласование преподавателей ожидается. Миграция не начата.

## 1. Цель и подтверждённые требования

Собрать код, задачи, PR, ревью и CI/CD фронта и бэка в `Cringe-Driven-Development-Team`. Использовать существующие репозитории `frontend` и `backend`, сохранив их задачи и номера. Учебные репозитории автоматически обновлять для рубежного контроля.

Пользователь подтвердил: преподавателям достаточно актуальных исходников и истории коммитов. Новые PR, ревью и обсуждения в учебных репозиториях не требуются. Преподаватели не участвуют в принятии синхронизационных PR.

Предлагаемые решения, которые утверждаются вместе с этой спецификацией: копировать только `main`, отключить Actions в учебных копиях, использовать отдельный SSH deploy key для каждой пары репозиториев, переключать фронт и бэк по очереди.

Разрешённая сейчас работа — подготовка документации и чтение текущих настроек. Создание ключей и секретов, изменение правил, push кода, отключение Actions и переключение production выполняются после согласования преподавателей и отдельного разрешения пользователя на миграцию. Утверждение документа само по себе не переключает репозитории.

## 3. Выбранная архитектура

| Основной репозиторий | Учебная копия |
|---|---|
| `Cringe-Driven-Development-Team/frontend` | `frontend-park-mail-ru/2026_2_Cringe_Driven_Development` |
| `Cringe-Driven-Development-Team/backend` | `go-park-mail-ru/2026_2_Cringe_Driven_Development` |

Разработка и ревью идут в основном репозитории. Успешная проверка принятого коммита `main` разрешает job синхронизации отправить именно этот коммит в учебный `main`. Production-деплой и синхронизация независимы: сбой деплоя не блокирует копирование проверенного кода, сбой копирования не запускает повторный деплой.

После завершения синхронизации обе вершины `main` имеют одинаковый SHA и одинаковое дерево файлов. При работающем CI возможна временная задержка учебной копии; мгновенное равенство после каждого push не обещается. Если новый `main` не прошёл проверки, учебная копия остаётся на последнем успешно синхронизированном коммите, а сбой виден в Actions.

Копируется история, достижимая из выбранного коммита `main`, включая исходные авторские и merge-коммиты. Ветки разработки, теги, releases, PR, апрувы, обсуждения, checks и артефакты Actions не синхронизируются. Старые PR остаются в учебных репозиториях. Файлы `.github/workflows` входят в дерево и копируются без изменений.

Рассмотрены два варианта: только `main` и все рабочие ветки. Выбран первый: для контроля достаточно принятого кода, а удаление и переименование временных веток не становятся частью синхронизации. Двусторонний обмен исключён: независимое изменение учебного `main` останавливает автоматическое обновление до разбора расхождения.

## 4. Импорт истории без пересоздания репозиториев

Репозитории задач не удаляются, не пересоздаются и не заменяются fork-репозиториями. Сохраняются их GitHub identity, issues, номера, assignees, связи sub-issues, карточки и поля доски. Новые PR продолжат общую с issues нумерацию GitHub; номера старых учебных PR не переносятся.

У истории заглушки и истории кода разные корни. Предлагается объединить их migration merge-коммитом с сохранением обеих линий истории. Результирующее дерево — дерево актуального учебного кода плюс согласованные изменения для работы в новой организации. Текущая вершина заглушки и зафиксированная вершина учебного кода должны быть предками результата.

Импорт оформляется отдельным PR в существующий репозиторий команды, принимается с обязательным ревью и обычным merge, без squash/rebase. Ветка этого PR строится от истории заглушки с локальным объединением истории приложения, чтобы GitHub мог сравнить её с текущим `main`. Тогда обновление основного `main` является fast-forward относительно истории заглушки, а первая отправка обратно в учебный `main` — fast-forward относительно прежней истории приложения. Переписывать старые SHA и применять force push не требуется. Ветки архивного состояния и Git bundles сохраняются перед импортом.

Во время переключения действует короткое окно без новых merge и изменений задач в мигрируемой паре. Если любой из зафиксированных SHA изменился, подготовленный импорт пересобирается и проверяется заново.

Особый случай — старые сообщения коммитов с `Closes #N` и похожими ссылками. В новом репозитории короткий номер имеет другой контекст. До импорта нужен отчёт о таких ссылках, снимок состояний задач и полей доски; Telegram-уведомления об импорте временно приостанавливаются. После импорта состояния сверяются со снимком: непреднамеренное закрытие или изменение поля восстанавливается до возвращения обычной работы; возможные системные события в timeline задачи остаются историей. Нельзя считать отключение workflows защитой от встроенного автозакрытия GitHub или штатных уведомлений самого GitHub. Исторические сообщения не переписываются; старые PR ищутся в исходном учебном репозитории.

Если перед переключением появились открытые PR, миграция соответствующего репозитория откладывается до их штатного принятия или согласованного переноса работы. Автоматически закрывать PR, терять ревью или выдавать пересозданный PR за перенесённый нельзя. Рабочие ветки, ещё не вошедшие в `main`, инвентаризируются; нужные ветки явно копируются в основной репозиторий с проверкой SHA, но не включаются в постоянную синхронизацию.

## 5. Контракт синхронизации

Общая реализация размещается в reusable workflow `sync-to-course.yml` репозитория `.github`. Фронт и бэк подключают её из CI отдельным job после проверок кода. Выбор учебного назначения задаётся фиксированной картой из раздела 3, а не произвольным пользовательским URL.

Вход — полный SHA проверенного коммита. Workflow проверяет соответствие основного репозитория, ветки `main` и назначения. Фронт разрешает синхронизацию после `check`; бэк — после `lint`, `test` и `docker`. Успех deploy/upload не является дополнительным условием. Для бэка ошибка сборки или публикации в job `docker` оставляет синхронизацию заблокированной.

Алгоритм:

1. Получить полную историю кандидата и актуальную вершину учебного `main`.
2. Равенство SHA — успешный повтор без записи.
3. Учебная вершина является предком кандидата — отправить только кандидат в `refs/heads/main` обычным push, без force и без `--mirror`.
4. Кандидат уже является предком учебной вершины и эта вершина принадлежит истории основного `main` — старый запуск завершить без отката копии.
5. Любое иное расхождение — ошибка с SHA и ссылками, без изменения учебной ветки.
6. После push повторно прочитать учебный ref и подтвердить ожидаемый SHA; при конкурентном продвижении подтвердить, что ожидаемый коммит является предком новой вершины и новая вершина есть в основном `main`.

Записи в одну учебную ветку сериализуются общей concurrency-группой. Порядок очереди не используется как гарантия: устаревший запуск обрабатывается правилами выше. Проверяется неизменяемый кандидат, а не скачанный позднее непроверенный HEAD. Скрипт не отправляет другие refs и не удаляет ветки.

Основной запуск — из CI. Повтор — rerun job либо ручной запуск с идентификатором CI run: из него берётся SHA, проверяются репозиторий, ветка и успех перечисленных проверок. Ручной запуск не позволяет отправить произвольный непроверенный SHA.

Ошибка синхронизации оставляет job красным и отправляет одно уведомление в существующий служебный Telegram-топик со ссылкой на запуск и учебный репозиторий. Отсутствующий секрет, отказ доступа, сетевой сбой и расхождение не превращаются в успех. Ошибка отправки уведомления также видна в логе. Оператор миграции и дальнейших сбоев — `YarikMix`.

## 6. Доступы и правила веток

Предпочтительная реализация этой версии — отдельный SSH deploy key с записью для каждого учебного репозитория. Приватная часть хранится только в соответствующем основном репозитории как `COURSE_SYNC_SSH_KEY`, публичная добавляется в учебный. Не использовать один ключ для двух назначений и не переиспользовать `ADD_TO_PROJECT_PAT`. SSH host key GitHub сверяется с официально опубликованным значением.

Преподавательское согласование должно включать право на автоматическое обновление `main` и предусмотренное ruleset исключение для выбранного механизма синхронизации. Существующий персональный bypass не является основанием молча обходить ревью. После настройки нужно проверить реальный push выбранной учётной возможностью; успешный `--dry-run` сам по себе не доказывает прохождение серверных правил.

Возможность deploy keys и нужного исключения подтверждается до переключения. Если политика организации запрещает эту схему, rollout останавливается; замена на GitHub App или PAT отдельно отражается в спецификации и согласуется. Fine-grained PAT нельзя заранее считать доступным outside collaborator или общим для двух чужих организаций. Эта версия не требует устанавливать приложение в преподавательские организации.

В основных репозиториях до обычной разработки включаются запрет force push/удаления `main`, PR, минимум один апрув, разрешение обсуждений и обязательные проверки кода. Для ревью менторам предоставляется нужный доступ; права синхронизации не дают исключения для принятия продуктовых PR. Job синхронизации не получает production-секреты и не запускается на PR или их коде до принятия.

## 7. Actions, секреты и production

В учебных репозиториях Actions отключаются настройкой репозитория до первого обновления от новой основной копии. Это сохраняет идентичность `.github/workflows`, предотвращает дублирование деплоя, уведомлений и синхронизации. Старые запуски остаются по действующим срокам хранения. Настройка проверяется отдельно; удалять YAML только в учебной копии нельзя, поскольку тогда дерево и SHA разойдутся.

На этапе импорта Actions основных репозиториев временно отключены; migration PR проверяется локально и проходит ревью, а обязательные удалённые CI checks включаются после импорта перед первым обычным PR. После merge сначала включаются проверки кода; production и синхронизация остаются за отдельными выключенными переключателями до завершения соответствующих проверок. Переключатели — `PRODUCTION_ENABLED` и `COURSE_SYNC_ENABLED`, только строка `true` включает действие, отсутствие означает выключенное состояние; это vars, а не разные файлы для копий. Production-переключатель охватывает запись релизов фронта, promote, rollback и backend deploy; сборка и публикация backend-образа остаются доступны для проверки до первого deploy. Пока Actions выключены, сохраняются состояния задач и доски по разделу 4.

Нужна инвентаризация repository/org/environment secrets и vars, правил environment `production`, ограничений веток и прав публикации Packages. Настройки GitHub не переносятся через Git. Значения существующих секретов берутся из исходного хранилища владельца или перевыпускаются; чтение списка имён через API не даёт их значений.

Подтверждённые имена секретов и зависимостей:

| Область | Что подготовить в основном репозитории |
|---|---|
| Общее | Доступ к org secrets `TELEGRAM_BOT_TOKEN`, `ADD_TO_PROJECT_PAT`, нужным `TELEGRAM_*` vars |
| Фронт, production | `S3_ACCESS_KEY`, `S3_SECRET_KEY`; vars S3 endpoint/bucket, CDN и топика релизов |
| Бэк, repository | `APIDOG_TOKEN` для `contract-drift.yml` |
| Бэк, production | `DEPLOY_SSH_KEY`, `SSH_KNOWN_HOSTS`, `ANSIBLE_VAULT_PASSWORD`, vars Telegram |
| Синхронизация | Отдельный `COURSE_SYNC_SSH_KEY` для каждого основного репозитория |

Environment `production` создаётся с эквивалентными ограничениями `main` и сохранением действующих правил приёмки. Общие и различающиеся между фронтом и бэком Telegram vars сверяются до включения уведомлений. Доступность org secrets существующим репозиториям проверяется заново.

Фронт сохраняет механизм upload, ручного promote и rollback релизов в S3/CDN. Адрес сайта, бакет и production-данные миграция не меняет. Во время переключения прекращаются старые upload/promote/rollback job; одновременно управлять указателем stable из двух репозиториев нельзя. Concurrency-группы разных репозиториев не дают общей блокировки.

Бэк сейчас публикует `ghcr.io/go-park-mail-ru/2026_2_cringe_driven_development`; это имя задано также в `infra/ansible/roles/app/defaults/main.yml`. После переноса публикуется `ghcr.io/cringe-driven-development-team/backend`, связанный с новым репозиторием. Сохраняется приватность образа. Нужно проверить `packages: write/read`, доступ CI и pull образа на сервере с временной авторизацией, а также обновить `app_backend_image` и все фактические overrides в infra. Старые образы сохраняются для отката; простое переключение git remote не заменяет эту работу.

До первого автоматического деплоя нового бэка нужен проверенный новый образ и отдельный контролируемый deploy с health check. Переход на новый registry path не должен менять БД или запускать новые миграции данных как часть переноса репозитория. Проверка контракта Apidog также включается в новом репозитории после настройки токена.

## 8. Общая автоматизация и документация

Обновляются `.github/CONTRIBUTING.md`, README и profile организации, README/инструкции агентов фронта и бэка, `cdd-tasks` и его справочник/проверки, релевантные ссылки в infra и документации. Карта «код и PR» начинает указывать на репозитории команды, а для обычного PR используется `Closes #N`. Префиксы задач, `web-N`/`api-N`, доска, Sprint и правило sub-issues сохраняются.

Из списка активных репозиториев `scripts/reminders.sh` после переключения пары удаляется её учебный репозиторий. Репозиторий команды уже включён в список. Это убирает напоминания о старых PR и проверку выключенной учебной «Автоматизации». Сбой новой синхронизации покрывается своим уведомлением и должен учитываться служебным мониторингом основных репозиториев; нельзя считать проверку одного `automation.yml` проверкой всех job.

Job `close` общего workflow не удаляется для всей организации автоматически: он может быть полезен другим межрепозиторным ссылкам. Упрощается процесс новых PR фронта и бэка; отключение старого поведения допускается только после проверки остальных потребителей. Исторические документы помечаются ссылкой на новую схему, а не переписываются как будто старой схемы не было.

На страницах основных репозиториев и организации указывается, где идут задачи и ревью и где находятся учебные копии. Отдельный README-коммит только в учебном репозитории запрещён контрактом идентичного дерева. Старые PR и сообщения `Merge pull request #N` остаются историей исходного учебного репозитория: номер в сообщении не создаёт новый PR у команды.

## 9. Порядок переключения и точки остановки

Это последовательность этапов для оценки дизайна; точные команды, изменения файлов и исполнители проверок будут в отдельном плане после ревью спецификации.

1. До ответа преподавателей: подготовить спецификацию и после её утверждения — план, инвентаризацию и локальные проверки без изменения удалённых репозиториев.
2. До окна миграции: получить согласование формата учебных копий и прямого обновления `main`; подтвердить механизм доступа, обязательное ревью у команды и источники секретов. Выбрать первым frontend, затем backend; между ними проверить работу первой пары. Если для какой-либо пары условия не выполнены, она продолжает работать по старой схеме.
3. Для выбранной пары: остановить merge, deployments и изменения задач, дождаться завершения активных job, повторить проверку PR/веток/SHA, сохранить Git bundles и экспорт GitHub-настроек/состояний. Поставить Actions обеих копий на паузу.
4. Подготовить и принять migration PR с обеими историями и нужными workflow. Проверить задачи/доску, восстановить непреднамеренные изменения импорта. Настроить доступы, protection и environments. Основной репозиторий до этого шага не объявляется рабочим для команды.
5. Включить Actions основного репозитория при выключенных production/sync, проверить CI и первый новый PR с ревью. После проверок разрешить sync и выполнить первое обновление учебной копии; убедиться в равенстве SHA и отсутствии запусков Actions в ней. Затем отдельно включить production после проверки runtime-зависимостей; для backend это новый GHCR path и infra. При неудаче соответствующий следующий этап не начинается.
6. Подтвердить health check, единственное место деплоя и работу уведомлений, обновить документацию/мониторинг, снять окно. Перенастроить git remotes у команды и явно перенести нужные рабочие ветки. Старый origin можно сохранить под именем `course` только для чтения.

Согласование преподавателей не требуется для локальной подготовки документов. Оно обязательно до изменения учебных правил и превращения репозиториев в копии. Между репозиториями нет атомарной транзакции: журнал этапов и повторяемость операций обязательны.

## 10. Проверка и критерии приёмки

- История приложения и история заглушки достижимы в основном `main`; исходные SHA приложения, authors и committers сохранены. Автоматическая синхронизация не применяет force push.
- После успешной синхронизации SHA и дерево `main` обеих копий равны; преподаватель может открыть прежнюю ссылку и историю принятого кода.
- Issues, их номера, состояния, assignees, sub-issues и карточки/поля доски соответствуют снимку, кроме явно согласованных рабочих изменений.
- Новый PR проходит обязательное ревью и проверки в организации команды; его merge закрывает корректную задачу и обновляет доску. Проверка на реальном GitHub входит в разрешённое окно миграции; предпочтительно закрытие штатной рабочей задачи вместо создания тестовых карточек.
- CI, upload/promote/rollback фронта, сборка/pull/deploy бэка и contract drift работают из новых репозиториев. В учебных копиях новые Actions не запускаются.
- Повтор синхронизации ничего не меняет; устаревший запуск не откатывает копию; расхождение учебного `main`, отказ доступа и сетевая ошибка дают диагностируемый сбой.
- Локальные тесты синхронизации используют временные Git-репозитории: проверяют импорт разных корней, fast-forward, повторы, устаревшего кандидата, расхождение и сохранение других refs. Ошибки авторизации/уведомлений покрываются заглушками, workflow — соответствующим линтером. Проверки не требуют записи в учебные репозитории.
- Старые и новые production-job не работают одновременно; проверен runtime health check, сохранён путь отката и отправляется уведомление о сбое sync.

## 11. Восстановление и откат

Сбой синхронизации сам по себе не требует возврата разработки: исправить доступ/соединение или разобрать расхождение и повторить отправку проверенного кандидата. Учебная копия временно остаётся на последнем успешном SHA. Чужой коммит не затирается и автоматически не сливается.

До первого нового рабочего merge можно отменить переключение пары: выключить новые production/sync и Actions основного репозитория, восстановить учебные настройки и прежнее дерево из сохранённого состояния, затем включить прежний deploy. Если migration-коммит уже попал в учебный `main`, обратный коммит должен явно восстановить дерево зафиксированного учебного SHA и пройти ревью, без переписывания истории. Слепой revert merge относительно первого родителя недопустим: этот родитель может содержать дерево заглушки. Отдельно восстановить состояния задач по снимку и исходные rulesets/environments/Actions. Восстановление не запускает старый deploy одновременно с новым.

После новых рабочих merge история команды не отбрасывается. Возврат к разработке в учебном репозитории выполняется как отдельное переключение: остановить запись, перенести весь принятый `main` обычным fast-forward, сверить историю и данные задач, перенести необходимые рабочие ветки, затем по очереди переключить CI/CD и доступ команды. Старую историю заглушки нельзя просто назначить обратно основным `main`.

Runtime-откат отделён от отката репозиториев: фронт возвращает прежний stable существующим rollback, бэк разворачивает сохранённый старый образ с нужным registry path. Старый GHCR package и необходимые для него read credentials не удаляются до завершения периода проверки. Git bundles содержат Git-объекты, а не резервную копию secrets, БД или GitHub metadata; последние учитываются отдельно.

## 12. Границы этой миграции

В объём входят две пары репозиториев, общий sync workflow, необходимые изменения CI/CD/infra, настройки GitHub и обновление правил задач. Изменения продукта, переработка Scrumban, перенос старых PR/reviews, двусторонняя синхронизация, копирование всех веток/тегов и перенос базы данных в объём не входят.

Ответ преподавателей и доступность deploy keys — внешние условия rollout. Их отсутствие не мешает ревью документа и локальной подготовке, но не заменяется предположением о согласии. Подробный план реализации создаётся после утверждения этой спецификации пользователем; выполнение плана и фактическое переключение согласуются отдельно.
