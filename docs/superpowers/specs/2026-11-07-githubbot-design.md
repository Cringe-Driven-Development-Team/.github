# GitHubBot: задачи GitHub и спринт из Telegram

Дата: 2026-11-07. Задача: [#60](https://github.com/Cringe-Driven-Development-Team/.github/issues/60).
Статус: согласовано; 2026-11-07 владелец поручил подготовить план реализации. Название изменено владельцем на GitHubBot. Технические решения, предложенные автором, отмечены в тексте.
Проверка отдельным агентом 2026-11-07: существенных вопросов, мешающих составить план, не осталось.

## Цель и границы

Участники команды создают, закрывают и назначают GitHub Issues из Telegram,
добавляют их в текущий Sprint и смотрят командный или личный список задач.
GitHub Issues и проект Scrumban №1 организации Cringe-Driven-Development-Team
остаются источником данных. Jira в качестве трекера не используется.

Первый выпуск предназначен для существующей Telegram-супергруппы команды.
Во всех её топиках доступны команды. Личные чаты, другие группы, PR-команды,
изменение статусов доски, создание итераций, плановые отчёты, AI и OAuth
пользователей в этот выпуск не входят. Временная недоступность при выкладке
допустима; требования обратной совместимости и безостановочного деплоя не нужны.

## Рассмотренные подходы

1. Форк AshokShau/GitHubBot: уже есть создание issues и OAuth, но назначение
   использует GitHub login, а Projects Sprint и нужные сводки отсутствуют.
   Пришлось бы сопровождать ненужные команды и MongoDB.
2. Activepieces CE: готовые Telegram/GitHub действия и GraphQL, но сопоставление
   людей, команды и спринты всё равно нужно реализовать в сценариях платформы.
3. Небольшой собственный бот с использованием имеющейся командной автоматики.
   Этот вариант выбран в обсуждении: узкий набор команд и существующие
   привязки участников позволяют обойтись без универсального продукта.

Техническое предложение автора: отдельный сервис `services/githubbot/` на
TypeScript/Bun, как соседний `webhook-alerts`. Telegram Bot API и GitHub API —
через `fetch`, без нового фреймворка и без запуска shell-команд из сообщений.
Небольшая локальная SQLite нужна для подтверждений обработки и незавершённого
выбора репозитория, а не для копии задач или спринтов.

## Команды и выбор задачи

| Команда | Результат |
| --- | --- |
| `/issue <Title>` | Создать issue; следующие строки сообщения — описание. |
| `/close [URL]` | Закрыть issue с причиной `completed`. |
| `/assign @tg-username [URL]` | Добавить исполнителя, сохранив остальных. |
| `/assignme [URL]` | Добавить отправителя команды, сохранив остальных. |
| `/unassign @tg-username [URL]` | Снять только указанного исполнителя. |
| `/tosprint [URL]` | Назначить текущий Sprint, не изменяя Status. |
| `/sprint` | Показать текущий спринт всей команды. |
| `/sprint @tg-username` | Показать задачи человека в текущем спринте. |

Основной способ выбрать issue — ответить командой на карточку GitHubBot
или на существующее уведомление о задаче от GitHub Monitoring.
Альтернатива — полная ссылка последним аргументом:

```text
/assign @username https://github.com/Cringe-Driven-Development-Team/backend/issues/123
/tosprint https://github.com/Cringe-Driven-Development-Team/backend/issues/123
```

Если нет ни ссылки, ни reply, бот показывает формат и ничего не меняет.
Если заданы оба способа, просит оставить один, даже когда ссылки совпадают.
Один `#123` не поддерживается. Указание репозитория в топике влияет только
на создание: команда с явной задачей может менять issue другого разрешённого
репозитория. `/sprint` тоже не ограничивается репозиторием текущего топика.

Поддерживаются обычные команды и `/command@BotUsername`; обращения к другому
боту игнорируются. Редактирование уже отправленного сообщения не выполняет
команду заново. Ответы бота приходят в тот же топик, что и команда.

### Карточки и ссылки

Карточка GitHubBot содержит название, `repo#N` и ссылку на issue; сообщение
после успешного изменения также содержит ссылку, чтобы на него можно было ответить.
Сам бот не пытается редактировать уведомления GitHub Monitoring.

Для собственных карточек и карточек доверенного бота уведомлений извлекается
каноническая ссылка задачи из основного заголовка (`text_link`) и кнопки
«Открыть задачу»/«Открыть комментарий». Ссылка комментария нормализуется до issue.
Ссылки в цитате описания не используются для выбора цели. Разные цели в
основных элементах карточки означают неоднозначность: нужна явная ссылка.
Одинаковые ссылки в заголовке и кнопке считаются одной целью.

Источник карточки проверяется по числовому ID бота, а не его имени.
Произвольный пользовательский текст и пересланная карточка не считаются
доверенной карточкой. Если reply недоступен или относится к другому топику
без доступного оригинала, бот просит полную ссылку.

Принимаются только HTTPS-ссылки `github.com` на `/OWNER/REPO/issues/N`,
без userinfo и нестандартного порта, для разрешённых репозиториев организации.
Произвольный URL не запрашивается: запрос GitHub API собирается из проверенных
owner/repo/number. API дополнительно проверяет, что это issue, а не PR.

## Создание и маршрутизация

| Топик | Репозиторий | Префикс по умолчанию |
| --- | --- | --- |
| Backend | backend | `Backend.` |
| Frontend | frontend | `Frontend.` |
| UX | figma | `Figma.` |

Маршрутизация задаётся парой `chat_id` + `message_thread_id`, а не названием.
В остальных топиках, включая Backend / Releases и Frontend / Releases,
бот показывает кнопки разрешённых репозиториев. До выбора issue не создаётся.
Выбор принимает только от автора исходной команды. В callback хранится
идентификатор заявки; repo берётся из разрешённой конфигурации, а не доверяется
произвольному callback payload. Повторное нажатие не создаёт вторую задачу.
Несколько `/issue` одного человека имеют независимые заявки.
Предложение автора: кнопки действуют 24 часа, затем нужно повторить `/issue`.

Конфигурация разрешённого репозитория содержит его имя, префикс по умолчанию
и допустимые префиксы. В `frontend` допустимы `Frontend.` и `BFF.`.
Если префикса нет, он добавляется; допустимый префикс сохраняется.
Известный префикс другой области — ошибка с подсказкой, без создания issue.
Пустой заголовок отклоняется до записи в GitHub. Текст после первой строки
сохраняется как описание без придумывания требований. Для Backlog допускается
один заголовок, согласно CONTRIBUTING.md.

При создании нет автоматического назначения исполнителя. Issue появляется
в Scrumban со статусом `Backlog` и пустым `Sprint`.
Бот сам обеспечивает добавление на доску и эти начальные значения, затем
проверяет их чтением. Существующий add-to-project workflow может работать
параллельно: добавление того же issue не должно создавать второй элемент.
Успех всей команды подтверждается после проверки доски.
Если issue уже создан, но настройка доски не завершилась, ответ содержит
ссылку на созданную задачу и конкретный незавершённый этап; второй issue не создаётся.

## Участники и права

Любой настроенный участник команды может выполнять все перечисленные команды
над задачами разрешённых репозиториев; роли автора, исполнителя и ментора
дополнительно не ограничивают эти действия. `/close` — явно запрошенное
ручное закрытие, без дополнительного подтверждения.

Допуск проверяется по Telegram `from.id` и разрешённому `chat_id`.
Анонимные сообщения от имени канала/группы и отправители-боты не выполняют
команды. Callback повторно проверяет автора, группу и право доступа.

Привязки задаются конфигурацией: Telegram user ID, актуальный username,
GitHub login. За основу берётся существующая `TELEGRAM_USER_MAP`;
она содержит ID, но не Telegram usernames. Секреты и реальные значения
не публикуются в исходниках. Username сравнивается без `@`, без учёта регистра;
дубли ID, логинов и usernames в конфигурации отвергаются при запуске.

`/assignme` использует ID отправителя. Остальные команды поиска человека
используют настроенный username, а не совпадение с GitHub login.
Неизвестное имя — ошибка. Владельцу нужно обновлять конфигурацию при смене
Telegram username; бот не может гарантированно разрешить произвольный
пользовательский `@username` через Bot API. Если у известного ID в полученном
сообщении username отличается от настройки, старый alias блокируется до
исправления конфигурации, но `/assignme` по ID остаётся доступен.

Перед добавлением исполнителя проверяется, что GitHub разрешает назначить
этот аккаунт в целевом репозитории. Остальные исполнители сохраняются:
используются операции добавления/удаления, а не замена всего списка.
Повторное назначение, снятие отсутствующего исполнителя и закрытие уже
закрытой задачи возвращают понятный ответ без лишних изменений.

## Sprint и сводки

Проект — Scrumban №1 организации; поле — `Sprint` типа iteration.
ID проекта, полей и итераций читаются через API, не зашиваются в код.
Текущая итерация определяется по дате Europe/Moscow:
`startDate <= today < startDate + duration дней`.
Нет подходящей итерации или найдено несколько — ошибка без записи.
Бот не создаёт спринты автоматически.

`/tosprint` обеспечивает членство issue в проекте и записывает только Sprint.
Для уже существующего элемента сохраняется прежний Status, включая отсутствие
значения. Если issue ещё не на доске, бот не устанавливает Status;
автоматика GitHub может задать его при добавлении. После записи Sprint
проверяется чтением. При внешнем изменении Status бот его не восстанавливает
поверх чужого изменения. Перенос из другой итерации в текущую разрешён
самой командой. Закрытый issue также можно включить в текущий спринт.

Сводки читают все страницы элементов проекта. Включают неархивированные
GitHub Issues разрешённых репозиториев с текущим iterationId, открытые
и закрытые. PR и draft items не являются задачами этого бота.
Для закрытого issue показываются и закрытое состояние, и Status доски,
если он ещё не обновился; пустой Status отображается как «без статуса».

Командная сводка: название и даты спринта, количество уникальных задач,
списки по исполнителям и группа «Без исполнителя». Задача с несколькими
исполнителями присутствует в каждом соответствующем списке, но в общем
количестве считается один раз. GitHub-исполнитель без Telegram-привязки
не теряется: показывается GitHub login. Личная сводка фильтрует по GitHub login.
В каждой строке — repo#N, название, Status, закрытость и ссылка.
Пустая выборка явно сообщает «задач нет». Длинная сводка разбивается
на последовательные сообщения без потери строк.

## Техническая основа и обработка сбоев

Предложение автора: отдельный Telegram bot token и один процесс с long polling
`getUpdates`, `allowed_updates=[message,callback_query]`. Входящий публичный
HTTP endpoint не нужен. Исходящий доступ к Telegram использует существующий
маршрут/прокси инфраструктуры при необходимости. Чужой установленный webhook
не удаляется молча: запуск останавливается с объяснением конфликта.

SQLite на постоянном volume хранит cursor polling, заявки выбора repo и журнал
команд с `update_id`, этапом выполнения, ссылкой на созданный issue и результатом.
Задачи, статусы и спринты каждый раз читаются из GitHub.
Очередь обрабатывается одним worker. Update сначала сохраняется, потом
подтверждается offset. После перезапуска сохранённая заявка не теряется,
а уже выполненная мутация не выполняется повторно.

Не обещается exactly-once между SQLite и GitHub. Если POST создания issue
получил неопределённый исход (обрыв после отправки или падение до сохранения
ответа), он автоматически не повторяется. Журнал помечает результат как
неопределённый; бот сообщает об этом и требует сверить GitHub перед новым
созданием. Уже известный issue URL сохраняется до дальнейших операций.
Повтор доставки Telegram update или двойной callback не создаёт новую заявку.
Повторяемые изменения проверяют текущее состояние перед возобновлением.
Сбой доставки ответа в Telegram не является поводом повторять GitHub-мутацию.

Таймауты и ответы API с ошибкой не превращаются в успех. Rate limits
учитываются по ответам провайдера. Ошибки логируются с ID команды и этапом,
без токенов и без дампа всего Telegram-чата. HTML сообщений экранируется.

GitHub credential — отдельная сервисная учётная запись/PAT с доступом к
Issues разрешённых repo и чтению/записи organization Projects. Личные OAuth
сессии не нужны. Действия в GitHub выполняются от имени сервисной учётки;
инициатор сохраняется в локальном журнале. Конкретные секреты выдаются при
развёртывании, а не при написании спеки.

### Что использовать из репозитория

- `scripts/sprint.sh`: запросы доски, пагинация, определение текущей итерации
  и формат ссылок. Сам скрипт не запускать из бота: он переносит задачи и
  отправляет плановые сообщения. Взять необходимые запросы в код нового сервиса.
- `services/webhook-alerts/src/config.ts`: источник существующей карты людей.
- `services/webhook-alerts/src/github.ts`: формат карточек уведомлений.
- `services/webhook-alerts/src/format.ts`: проверенные правила экранирования
  и разбиения сообщений; переиспользовать подходящие чистые функции без
  загрузки всего сервиса уведомлений.
- `.github/workflows/add-to-project.yml`: существующее добавление на доску
  и обработка закрытия; бот не заменяет жизненный цикл релизных статусов.

Разбиение файлов, внутренние типы, SQL-схема, параметры повторов и точные
тексты ошибок остаются исполнителю, в рамках описанного поведения.

## Telegram: обязательная проверка reply

Telegram FAQ указывает, что при включённом privacy mode reply к сообщению
бота A может не доставляться боту B. Для требуемых коротких команд ответом
на GitHub Monitoring у GitHubBot выключается privacy mode; проверяется
фактическая настройка группы после добавления бота. Администраторские права
только ради чтения не требуются, если privacy отключён.

Бот получает команду человека с `reply_to_message`, а не подписывается на
сообщения другого бота. Bot API описывает оригинал для reply в том же чате
и топике, но полнота вложенных карточек конкретного sender ещё не проверена
живым экспериментом. До завершения реализации обязательна проверка:
человек отвечает `/assignme` и `/tosprint` на настоящее уведомление GitHub
Monitoring, GitHubBot получает команду, оригинал и корректную цель.
Если этого недостаточно, требование не считается выполненным; необходимо
разобрать транспорт, а не молча оставить только явные ссылки.

## Развёртывание и границы репозиториев

Код, тесты, контейнер и сборка образа — в `.github`; настройка сервиса,
volume, секретов и исходящего Telegram-доступа — в `infra`.
На этапе плана оформить инфраструктурную sub-issue к #60: её PR закрывает
sub-issue, а #60 закрывается после доставки и общей приёмки. Если кодовый
PR должен влиться раньше, он содержит `Part of .../.github/issues/60`;
родитель закрывается после проверки всех частей, не преждевременно.
Разработка локально не блокируется ожиданием выкладки infra.

Перед запуском нужно прочитать реальные chat/topic IDs, ID бота уведомлений,
заполнить разрешённые repo с префиксами и привязки участников. Их значения
не выведены из скриншота и не выдуманы в этой спеке.

## Проверка и приёмка

Точечные тесты покрывают:

1. Маршрутизацию трёх топиков и кнопки в остальных; callback чужого автора,
   повторный callback, независимые заявки и сохранение после перезапуска.
2. Создание с допустимым/отсутствующим/чужим префиксом; пустой заголовок;
   Backlog и пустой Sprint после чтения результата.
3. Все пять изменяющих команд через reply и URL; отсутствующий/двойной
   способ, несколько целей, ссылка в цитате, чужая организация, URL PR.
4. Доступ по ID, неизвестный username, сменившийся alias, `/assignme`,
   сохранение остальных assignees и отказ GitHub в назначении.
5. Границы дат, отсутствие текущего Sprint, перенос из другой итерации,
   сохранение Status, пагинацию, закрытые задачи и пустую личную сводку.
6. Повтор update, перезапуск, частичный успех создания, неопределённый POST,
   ошибку отправки Telegram без повторного создания issue.

После тестов с API-заглушками проверить реальный бот в группе: создание
в трёх топиках и через кнопки, команды ответом на обе разновидности карточек,
команды со ссылками, назначение по пингу, `/tosprint` и обе сводки.
Проверить сохранённые значения GitHub API, а не только текст ответа.
Фикстуры реальных Telegram updates сохранять без токенов и персональных данных.
