# Уведомления о выпусках фронта через webhook-сервис

Статус: подход согласован владельцем; после обсуждения подтверждено сохранение Board в Actions.
Проверка независимым инженером: важных вопросов для составления плана не осталось.

## Зачем

Уведомления о merge queue, готовом выпуске, выкатке и откате фронта отправляет
существующий сервис `.github/services/webhook-alerts`, получая события GitHub.
CI/CD выполняют операции и записывают результат, но больше не отправляют эти
Telegram-сообщения. Сверка Scrumban остаётся отдельной работой Actions.

На PR frontend#134 организационный webhook уже принял `pull_request.enqueued`
2026-11-01 в 20:07:26.936 UTC, ответив HTTP 202 за 0,58 секунды. Старый Actions
sender отправил Telegram-сообщение лишь в 20:13:13 UTC, после мержа в 20:08:15 UTC.
В текущем `formatGithub` действия `enqueued` и `dequeued` не обрабатываются.

## Согласовано с владельцем

- Переносим перечисленные уведомления фронта в существующий webhook-сервис.
- Источник готовности и результата — запись операции в GitHub Deployments.
  Завершение job используется для ошибок, которые запись операции не покрывает.
- Устаревшее «PR поставлен в очередь» отменяется перед отправкой, если PR уже
  влит или больше не находится в очереди.
- Сохраняем ранее согласованные названия PR, ссылки на задачи, кнопки и
  `Health Check` с индикатором результата.
- Board остаётся отдельным workflow: сверка восстанавливает фактические статусы
  независимо от своевременности Telegram-событий. `release-status.yml` сохраняется
  только для Board и ручной сверки. Перенос Project API в сервис не входит в работу.

## Подходы

1. Выбран владельцем: `pull_request` для очереди, `deployment_status` для готового
   выпуска и выкатки/отката, `workflow_job.completed` для оставшихся ошибок.
   Источник соответствует фактической операции, готовность не ждёт весь CI.
2. Завершение jobs как основной источник: проще подписки, но результат job может
   отличаться от результата операции, например production уже проверен, а retention
   упал. Вариант не выбран.

Встраивание Telegram-отправок обратно в CI/CD также не выбрано: владелец запросил
использовать уже подключённый webhook-сервис.

## Границы

Работа затрагивает три репозитория: `.github` — обработчики, хранение, sender и
конфигурацию; `frontend` — метаданные операций, отчёты и удаление отправок из Actions;
`infra` — закреплённый image сервиса и его конфигурацию. Рабочие задачи/PR разделяются
по правилам CDD, с явными ссылками на общий дизайн и порядком завершения.

Начальный allowlist — только `Cringe-Driven-Development-Team/frontend`, ветка `main`.
Существующие общие PR/issue/review/push-алерты и Apidog не меняют назначения,
фильтров или формата. Новые release-сообщения идут в действующую тему выкаток,
через действующего GitHub-бота и Telegram proxy; topic передаётся настройкой
`TELEGRAM_RELEASES_TOPIC_ID`. Бот/чат/тема не заменяются значениями по умолчанию.

Не создаём новый сервис, брокер сообщений, периодический поиск всех PR/задач,
автоматический deploy из Telegram, страницу отчёта или требование высокого uptime.
Не переносим Project PAT и работу с доской в webhook-сервис. CD/Rollback и проверки
образа, ассетов, HTML/RPC продолжают выполняться в Actions.

## Источники и сообщения

| Событие | Условие | Результат |
| --- | --- | --- |
| `pull_request.enqueued` | PR направлен в main выбранного репозитория | Уведомление о текущей постановке в очередь |
| `pull_request.dequeued` | Тот же PR; причина не MERGE | Уведомление о снятии с очереди с безопасно отображённой причиной |
| `pull_request.closed` | `merged=true` | Сохраняется существующая общая карточка о мерже |
| `deployment_status.created` | `release-artifacts`, task publish, state success | «Релиз фронта залит, ждёт выкатки» |
| `deployment_status.created` | `production`, task/action deploy или rollback, in_progress | Человекочитаемое начало операции и кнопка логов |
| `deployment_status.created` | Та же операция, state success/failure/error | Результат выкатки/отката и Health Check |
| `workflow_job.completed` | Проверенная job Publish release, CD или Rollback завершилась ошибкой/отменой | Ошибка, ещё не покрытая записью операции |

`pending`, `queued` и чужие environments не образуют release-уведомления.
`release-automation` никогда не служит источником: иначе получится рекурсия.
`dequeued` с причиной MERGE не вызывает сообщение о неудаче. GitHub App и событие
`merge_group` для этого не нужны. Проверка Check сама по себе не означает готовность
релиза и не создаёт второй release-алерт; существующие другие CI-алерты не расширяем.

## Отмена устаревшего enqueue

До подготовки и непосредственно перед каждой реальной отправкой/повтором читаем
актуальные merged/closed и `mergeQueueEntry` PR. Отсутствие entry, закрытие или merge
означают `skipped` с причиной в журнале, без отправки Telegram.

Сообщение связывается с ID актуальной MergeQueueEntry. Повторные доставки одного
enqueue не создают вторую карточку для этой entry. Если PR сняли и поставили снова,
новая entry допускает новое уведомление, а ожидающее сообщение старой entry
пропускается. Текст и инициатор относятся к подтверждённой текущей entry.

При ошибке GitHub API не делаем вид, что очередь всё ещё актуальна: откладываем
проверку, остальные сообщения продолжают обрабатываться. Между последней проверкой
и HTTP-вызовом Telegram возможен merge; абсолютной атомарности двух сервисов нет.
Уже отправленные сообщения автоматически не удаляем и не редактируем.
Перед отправкой dequeued также проверяем актуальность: если PR уже снова в очереди
или влит, запоздавшее сообщение о снятии пропускается.

## Результат операции и доверие к источнику

Проверка HMAC и запись raw delivery до HTTP 202 сохраняются. Подписка организации
расширяется `deployment_status` и `workflow_job`; `pull_request` уже подключён.

Для release-события проверяем репозиторий, environment/task, SHA, assets path,
digest BFF и точный Actions run из `ci_run`/`run`. По API подтверждаем ожидаемый
workflow CI/CD/Rollback, ветку main и допустимое событие push/workflow_dispatch.
Для CI SHA операции должен совпадать с run head SHA; для CD/Rollback проверяем
целевой SHA отдельно от head SHA workflow, поскольку можно выкатывать старый выпуск.
Произвольная вручную созданная запись не выдаётся за результат доверенного workflow.

Run в момент регистрации может ещё выполняться. Не ждём completed ради принятия
подтверждённого результата операции: сохранённый success release-artifacts означает
готовые проверенные артефакты, success production — пройденную проверку запуска.
Не повторяем сетевой Health Check и проверки образа в webhook-получателе.

Для неуспешной production-записи уточняем Health Check и этап сбоя по steps
конкретной job этого run через Actions API. Недоступность этих данных даёт
`Health Check ⚪` и ссылку на логи, без утверждения, что прод здоров или не менялся.
Success production даёт `Health Check ✅`; failure Health check — `❌`.

Production record создаётся непосредственно перед Switch BFF, после подготовки
инструментов и SSH, вместо прежнего Telegram-шагa Deployment started. Так in_progress
обозначает начало переключения; сбой подготовки покрывается job-событием.
Окончательный production status остаётся после Health check, как сейчас.

## Метаданные и полный отчёт

Сохраняем имеющиеся image_ref/assets/ci_run либо action/run. Producer добавляет
небольшие метаданные: SHA базы сравнения либо null, URL полного отчёта Summary
и номер попытки Actions run. Проверяется именно эта попытка, а не последняя
попытка run на момент запоздавшей доставки.
Actor/triggering_actor читается из проверенного Actions run. Не помещаем весь
список PR и задач в Deployment payload и не вводим второй источник состояния прода.

Для публикации база — предыдущий проверенный опубликованный предок целевого SHA.
Для CD — последний подтверждённый production на момент начала операции; для rollback
тот же before SHA, а диапазон отменённых изменений считается target..before.
При отсутствии базы выводим честное «база неизвестна», не сравниваем с выдуманным SHA
и не сканируем всю историю задач ради первого выпуска.

Полный отчёт с PR и закрывающими задачами формирует отдельный шаг существующего
CI/CD/Rollback и записывает в собственный GITHUB_STEP_SUMMARY до регистрации операции.
Этот шаг не отправляет Telegram. Чтение состава ограничено конкретным диапазоном:
все страницы сравнения коммитов и связанные с ними PR, затем только их closing issues.
Не используем общий обход всех merged PR/всех issues. Критерий включения PR — его
merge commit в диапазоне; заголовок коммита и имя base-ветки не заменяют проверку.

Webhook-сервис получает состав для того же диапазона точечными API-запросами и
формирует существующие карточки; ссылка на полный список ведёт на Summary исходного
run. Обогащение ссылками не меняет подтверждённый результат операции. При его сбое
отправляем основной результат с пометкой о недоступном составе и логами.
«Все PR выпуска» показываем только при существующем полном отчёте.

Для 1 PR сохраняем кнопку PR, для 2–6 — PR #N по две в строке, для большего числа
— «Все PR выпуска». Ссылки на названия задач остаются в тексте; начало выкатки
показывает названия PR вместо одного SHA. Сохраняем кнопки prod/rollback/deploy/logs,
ограничение длины Telegram и безопасное HTML-экранирование. Транспорт и SQLite
расширяются для многострочной inline keyboard; старые карточки с одной/двумя кнопками
продолжают использовать тот же sender, без переписывания их обработчиков.

Неудача подготовки отчёта не запрещает публикацию/выкатку. Report URL в таком случае
не рекламируется как полный отчёт. Ни тесты, ни webhook-сервис не пишут в чужой CI Summary.

## Доставка, ошибки и порядок

Raw deliveries, outbox и дедупликация X-GitHub-Delivery остаются в существующем SQLite.
Дополнительно фиксируем семантические ключи: queue по entry ID, ready по SHA,
start по production deployment ID. Терминальный result и соответствующий job fallback
делят ключ repository + operation kind + run ID + attempt: один результат операции
не дублируется, даже если job-событие обогнало status и запись ещё не видна по API.
Уведомление о Retention использует отдельный ключ run ID + attempt.
Повторный status success или повтор job-события не отправляет тот же результат снова.

Пропущенный ready для выпуска, уже входившего в успешный production, не отправляется;
последующий rollback не делает старый ready актуальным. Проверяется история
production, но не Project API и не каталог всех задач. Старая production start,
если операция уже завершена, также пропускается. Неуспешные результаты операций
сохраняем даже при более позднем успешном запуске, явно указывая исходный run/время.

Если job провалилась до создания production/release-artifacts, отправляем один
fallback с этапом сбоя и логами. Если терминальный результат уже записан, job-событие
не дублирует его независимо от порядка webhook-доставок. Проверка делается по API
записей операции, а не только по тому, какая delivery уже обработана сервисом.
Если production success есть, но позже упал Retention, это отдельное предупреждение
об очистке: не переписываем успешную выкатку как неудачную.

Обработка enqueue имеет быстрый независимый проход и не ждёт обогащения release-карточек,
отчётов или Project API. Используем существующий SQLite/outbox и sender; не вводим
общий mutex на сетевые запросы release-обогащения. План должен выбрать минимальный
способ независимой подготовки быстрых PR-событий; общий rate limit Telegram сохраняется.

Для новых release-сообщений сохраняем осторожное отношение к неизвестному исходу
Telegram: подтверждённый 429 допускает retry, сетевой timeout/неоднозначный ответ
или сбой записи после принятия Telegram требует ручной проверки и не запускает
слепую повторную отправку. Это отдельная политика новых сообщений, существующая
at-least-once политика обычных GitHub/Apidog карточек не меняется.

## Переключение и удаление прежнего пути

Это разовое согласованное переключение, без поддержки двух контрактов и dual send.
После реализации проверяется сервис, producer и подготовленная конфигурация; во время
переключения фиксируется UTC-граница в постоянном состоянии сервиса, старые отправки
останавливаются и новая подписка/обработка включается. События до границы автоматически
не рассылаются. Исторические Deployment без новых notification-метаданных остаются
историей для доски/выбора версии, а не кандидатами новой рассылки.

Если между действиями попали реальные события, сверяем их с журналом старого sender
и выполняем адресное восстановление, без массового replay старой очереди. Старые jobs
не должны продолжать отправку после включения нового пути. Существующие SQLite raw
deliveries и история GitHub Deployments не удаляются и не переписываются.

Из frontend удаляются шаги release notify и notification-job Release status,
enqueue/workflow_run-подготовка Telegram, notify-pending и запись release-automation
для новых событий. Исторические записи сохраняются. Существующий release-status
workflow остаётся только для Board и ручной сверки, без Telegram-секретов и writer
доставки. Чистые helpers отчёта сохраняются отдельно от транспорта.

Деплой webhook image и изменение подписок — операционные шаги после проверки кода;
эта спецификация их сейчас не выполняет. Выкатка фронта в production для проверки
не запускается автоматически: она требует отдельного поручения владельца.

## Приёмка и проверка

- Signed enqueued проходит HTTP → SQLite → актуальность PR → sender без Actions,
  без запроса доски, каталога задач и истории публикаций.
- Merged/closed/dequeued перед первой отправкой и перед retry дают skipped;
  re-enqueue и повтор доставки не создают устаревший алерт или дубль.
- Заторможенное release-обогащение и недоступный Project не мешают enqueue.
- Success release-artifacts отправляет ready, пока исходный CI ещё выполняется;
  общий результат CI из-за course-sync не отменяет готовность артефактов.
- Проверены source allowlist, trusted workflow/run, SHA/digest/assets, разные
  source/target SHA CD, отсутствие рекурсии на release-automation.
- Ошибки до записи операции, failure Health check, success + retention failure,
  отмена, повторные и переставленные события покрыты осмысленными тестами.
- Форматы, task links, 1/6/7 PR, полный Summary, inline keyboard, HTML/лимиты,
  отсутствие утечки тестового Summary и неизвестный исход Telegram проверены.
- Существующие GitHub/review/Apidog тесты проходят; секреты и payload не попадают
  в диагностические логи. БД сохраняется и переживает рестарт контейнера.
- При переключении есть проверенный image digest, активная подписка, один sender
  для каждого вида событий, адресная проверка фактического message_id. В отчёте
  различаем время получения GitHub delivery и время принятия Telegram.

Не обещаем фиксированное число секунд: GitHub может задержать/переставить webhook,
а Telegram — ограничить отправку. Убираем собственное ожидание Actions и доски.

## Решения агента на проверку владельцу

Сохранить Summary внутри исходных CI/CD как полный отчёт; добавить уведомление о
снятии PR с очереди с исключением MERGE; предупреждать отдельно о Retention после
успешного production; пропускать устаревший start и ready; применять осторожную
политику неизвестной доставки только к новым release-сообщениям. Эти детали не
приписываются владельцу до подтверждения документа.

Точную структуру модулей, имена CLI-команд отчёта, минимальное представление ключей
и статусов в SQLite и организацию быстрых PR-проверок определяет план реализации.
Новых зависимостей по умолчанию не требуется.
