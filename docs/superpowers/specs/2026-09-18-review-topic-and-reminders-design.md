# Топик Code Review и напоминания о ревью

Дата: 2026-09-18
Статус: дизайн согласован в чате, ждёт вычитки спеки

## Зачем

1. Сообщения про ревью тонут в общем топике GitHub среди пушей, задач и мержей. Для них заведён отдельный топик «Code Review» в том же чате.
2. Ревьюверы забывают про запрошенные ревью. Нужно регулярно напоминать тем, кто висит в Reviewers открытого PR и ещё не ответил.

Обе части живут в `Cringe-Driven-Development-Team/.github`. Файлы-вызовы в подключённых репозиториях не меняются.

## Часть 1. Маршрутизация сообщений

Новая переменная `TELEGRAM_REVIEW_TOPIC_ID` — ID топика «Code Review». Заводится там же, где остальные `TELEGRAM_*`: на уровне организации (видимость all) и на уровне репозитория во frontend и backend. Пустая — всё идёт в `TELEGRAM_TOPIC_ID`, как раньше.

| Событие | Топик GitHub | Топик Code Review |
|---|---|---|
| `pull_request: opened` (не черновик), `ready_for_review` | «🔀 Открыт pull request»: `автор: <пинг> · ревьювер: <текстом>` | если в Reviewers кто-то есть — одно «👀 Запрошено ревью»: `автор: <текстом> · ревьювер: <пинг каждого>` |
| `pull_request: review_requested` не у черновика, позже 60 секунд после создания PR | — | «👀 Запрошено ревью»: `автор: <текстом> · ревьювер: <пинг добавленного>` |
| `pull_request: review_requested` у черновика или в первые 60 секунд | — | — (ревьювер уже в сообщении на opened/ready) |
| `pull_request_review: submitted`, approved / changes_requested | — | «👍 Апрув» / «✋ Запрошены правки», пинг автора PR |
| напоминания по расписанию (часть 2) | — | дайджест «⏰ Ждут ревью» |

Правило пингов в Code Review: ссылку-упоминание получает только тот, кому надо действовать — ревьювер на запросе и напоминании, автор на ответе ревью. Остальные логины — простым текстом. В топике GitHub сообщения о PR выглядят как раньше, только ревьюверы в «Открыт pull request» — текстом.

Остальные события (пуши, задачи, мерж и закрытие PR) не меняются.

### Изменения в `telegram.yml`

- env: `REVIEW_TOPIC: ${{ vars.TELEGRAM_REVIEW_TOPIC_ID }}`.
- Отправка выносится в функцию `send <топик> <текст> <разметка>` с проверкой ответа Telegram: на opened/ready с ревьюверами один запуск шлёт два сообщения в разные топики.
- `mention` получает режим «без ссылки» — для ревьюверов в топике GitHub и автора в «👀».

## Часть 2. Напоминания по расписанию

### Файлы

- `.github/workflows/reminders.yml`:
  - `schedule: - cron: '0 7,12,17 * * *'` — 10:00, 15:00, 20:00 МСК (cron в UTC; GitHub может запускать с опозданием на 5–15 минут);
  - `workflow_dispatch` с параметром `min_hours` (по умолчанию `4`) — для ручных проверок;
  - `permissions: contents: read`;
  - шаги: `actions/checkout` самого `.github`, затем `bash scripts/reminders.sh`.
- `scripts/reminders.sh` — вся логика. Отдельный файл, а не блок в YAML: workflow выполняется в самом `.github`, скрипт доступен после checkout и тестируется напрямую.

Env скрипта: `GH_TOKEN` (`github.token`), `TOKEN` (`secrets.TELEGRAM_BOT_TOKEN`), `CHAT` (`vars.TELEGRAM_CHAT_ID`), `TOPIC` (`vars.TELEGRAM_REVIEW_TOPIC_ID || vars.TELEGRAM_TOPIC_ID`), `MAP` (`vars.TELEGRAM_USER_MAP`), `MIN_HOURS` (`inputs.min_hours || 4`).

### Какие репозитории

Список в скрипте: `.github`, `docs`, `static`, `infra`, `react` из Cringe-Driven-Development-Team, `frontend-park-mail-ru/2026_2_Cringe_Driven_Development`, `go-park-mail-ru/2026_2_Cringe_Driven_Development`. Название стороны — как в `telegram.yml`: frontend / backend / имя репозитория.

### Данные

Один GraphQL-запрос `gh api graphql`, по алиасу на репозиторий. Для каждого открытого PR (`states: OPEN`, до 50 на репозиторий):

- `title`, `url`, `isDraft`, `createdAt`, `author.login`;
- `reviewRequests` — кто сейчас в Reviewers (только `User`; запросы у команд пропускаются);
- `timelineItems(last: 100, itemTypes: [REVIEW_REQUESTED_EVENT, READY_FOR_REVIEW_EVENT])` — когда у кого запрошено ревью и когда PR переведён в Ready.

GitHub сам убирает человека из Reviewers, когда тот оставил ревью, и возвращает при повторном запросе. Поэтому «не ответил» = «сейчас в `reviewRequests`».

### Правило

- Черновики пропускаются.
- Для каждого ревьювера из `reviewRequests`: «ждёт с» = позднейшее из (последний `ReviewRequestedEvent` у этого логина, последний `ReadyForReviewEvent` PR). Если запроса у этого логина в истории нет (ушёл за последние 100 событий) — от `createdAt` PR.
- Ждёт `MIN_HOURS` часов и больше — попадает в дайджест.

### Формат

Одно сообщение за запуск в топик Code Review:

```
⏰ Ждут ревью

• backend · API-3: Подготовить проект
  <пинг blackHATred> · ждёт 1 д 5 ч
  <пинг ManInTheCoat> · ждёт 6 ч
• frontend · WEB-25: Форма входа
  <пинг YarikMix> · ждёт 4 ч
```

- Заголовок PR — ссылка на PR, экранирован для HTML.
- Время: `N ч` меньше суток, `N д M ч` дольше (`M = 0` → `N д`).
- PR отсортированы по самому долгому ожиданию среди их ревьюверов, ревьюверы внутри PR — тоже.
- Больше 20 PR — первые 20 и строка «…и ещё N».
- Пинг — по `TELEGRAM_USER_MAP`, логина нет в карте — текстом.
- Ждущих нет — сообщения нет.

### Предупреждение об отключении cron

В публичном репозитории GitHub отключает cron после 60 дней без активности; что считается активностью, в документации не уточнено. Обходить это не будем (сервис keepalive-workflow, который это делал, заблокирован GitHub). Вместо этого: если последний коммит в `main` репозитория `.github` старше 50 дней, в конец дайджеста добавляется

> ⚠️ Напоминания отключатся примерно через N дней без коммитов в .github. Сделайте любой коммит или включите вручную: `gh workflow enable reminders.yml -R Cringe-Driven-Development-Team/.github`

Ждущих PR нет — предупреждение уходит отдельным сообщением. Дата последнего коммита берётся из checkout (`git log -1`).

### Токен

Встроенный `GITHUB_TOKEN` репозитория `.github`: чтение открытых PR публичных репозиториев не требует прав на них. Проверяется первым ручным запуском. Если GraphQL откажет по репозиториям других организаций, запасной вариант — секрет `ADD_TO_PROJECT_PAT` (личный токен ментора, решение за ним).

### Ошибки

Ошибка GraphQL или отказ Telegram — выход с кодом 1, джоба красная; GitHub пришлёт письмо тому, кто последним менял cron.

## Проверка

**Локально:**

- `tests/telegram.sh`: заглушка `curl` сохраняет каждое сообщение вместе с `message_thread_id`. Новые случаи: PR с ревьюверами (GitHub — «Открыт» с ревьюверами текстом; Code Review — «👀» с пингами), PR без ревьюверов (одно сообщение в GitHub), «👀» для добавленного позже — в Code Review, апрув и правки — в Code Review, без `TELEGRAM_REVIEW_TOPIC_ID` — всё в обычный топик.
- `tests/reminders.sh`: заглушки `gh` (JSON-фикстуры) и `curl`, «сейчас» и дата последнего коммита задаются через env. Случаи: нет PR — тишина; черновик пропущен; 3 ч 59 мин — нет, 4 ч — да; Ready позже запроса — счёт от Ready; два ревьювера — две строки; сортировка; больше 20 PR — «…и ещё N»; логин без карты — текстом; предупреждение о 50 днях, в том числе отдельным сообщением без PR; ошибка `gh` — выход 1.
- `tests/lint.sh` проверяет shellcheck'ом ещё и `scripts/*.sh`.

**На живых событиях:**

| Что | Как | Ожидание |
|---|---|---|
| раскладка по топикам | PR в `.github`, открытый через веб-форму с ревьювером | GitHub — «Открыт» с ревьювером текстом; Code Review — «👀» с пингом |
| доступ к PR других организаций и дайджест | после мержа `gh workflow run reminders.yml -f min_hours=0`, пока в каком-нибудь PR висит ревьювер | запуск зелёный, дайджест в Code Review |

## Порядок выкатки

1. Завести `TELEGRAM_REVIEW_TOPIC_ID` в организации и во frontend и backend. До мержа её никто не читает.
2. PR в `.github` с частями 1 и 2; живая проверка раскладки; мерж.
3. Ручной запуск `reminders.yml` с `min_hours=0` — проверка токена и дайджеста.

## Вне рамок

- Напоминания авторам PR с запрошенными правками.
- Запросы ревью у команд GitHub.
- Настройка порога и расписания без правки кода.
- Обход автоотключения cron.
