# Комментарии ревью, одобренные PR и служебные алерты

Дата: 2026-09-18
Статус: дизайн согласован в чате, ждёт вычитки спеки

## Зачем

Три слепые зоны в уведомлениях и один новый репозиторий:

1. Ревью «только с комментариями» не даёт сообщения: автор PR не узнаёт о замечаниях, если ревьювер не нажал «Request changes».
2. Одобренный, но не влитый PR выпадает из напоминаний: в Reviewers уже никого нет.
3. За самими уведомлениями никто не следит: письмо о падении job получает тот, кто вызвал событие (студент), а истечение `ADD_TO_PROJECT_PAT` молча останавливает добавление карточек на доску.
4. Появился репозиторий `Cringe-Driven-Development-Team/figma` — его нужно подключить к системе.

Всё, кроме подключения `figma`, правится только в `Cringe-Driven-Development-Team/.github`.

## Часть 0. Репозиторий `figma`

Публичный, секреты и переменные организации ему доступны, правил ветки нет.

- В `figma`: PR из ветки `chore/reusable-workflows` с тем же `automation.yml`, что в остальных репозиториях (README `.github`, раздел «Как подключить репозиторий»).
- В `.github`: `figma` добавляется в список репозиториев `scripts/reminders.sh` (напоминания и служебные проверки) и в таблицу `profile/README.md`.

## Часть 1. Ревью с комментариями (`telegram.yml`)

### Проблема шума

«Add single comment» и ответ в ветке обсуждения — каждый раз отдельное событие `pull_request_review: submitted` с состоянием `commented`. Пять одиночных комментариев — пять событий.

### Склейка серии

- У job `notify` появляется `concurrency` с `cancel-in-progress: true`. Группа:
  - для `pull_request_review` — `tg-review-<репозиторий>-<номер PR>-<логин ревьювера>`;
  - для остальных событий — уникальная (`tg-<run_id>`), они друг друга не отменяют.
- На `commented` скрипт ждёт `REVIEW_WAIT` секунд (по умолчанию 180). Новый комментарий того же ревьювера к тому же PR отменяет ждущий запуск и начинает отсчёт заново. Сообщение уходит, когда ревьювер затих на 3 минуты.
- Апрув и «Request changes» попадают в ту же группу: они отменяют ждущую серию и уходят сразу, без ожидания.
- Отменённые запуски видны в Actions серыми — это ожидаемо. Служебные проверки (часть 3) считают сбоем только `failure`.

### Подсчёт

После ожидания (для `commented`) или сразу (для апрува и правок) скрипт читает `GET /pulls/N/reviews` и берёт серию: идущие подряд с конца отправленные ревью этого логина с промежутками меньше `REVIEW_WAIT`. Число комментариев серии = inline-комментарии этих ревью (`GET /pulls/N/comments`, фильтр по `pull_request_review_id`) + ревью серии с непустым общим текстом.

API недоступен — сообщение уходит без числа, в лог `::warning::`.

### Сообщения (топик Code Review)

```
💬 Комментарии к PR · backend
API-3: Подготовить проект к работе          ← ссылка на PR
автор: <пинг MrDuckVC> · ревьювер: blackHATred
5 комментариев
[Открыть ревью]                              ← кнопка: первое ревью серии
```

- Пингуется автор PR — действовать ему; ревьювер текстом.
- «👍 Апрув» и «✋ Запрошены правки» получают строку `N комментариев`, если в серии они есть, и ту же кнопку.
- Склонение: 1 комментарий / 2 комментария / 5 комментариев.

### Молчим

- ревью оставил автор PR (ответы в ветках обсуждения);
- ревью оставил бот (`review.user.type == Bot`).

### Известная неточность

Если GitHub продержит запуск в очереди дольше минуты, число комментариев в редком случае будет неточным. Пинг не теряется, все комментарии автор видит по кнопке.

## Часть 2. «✅ Одобрены, ждут мержа» (`scripts/reminders.sh`)

### Правило

Статус считается самостоятельно: в репозиториях без правил ветки GitHub не заполняет `reviewDecision`. PR попадает в блок, если одновременно:

- открыт и не черновик;
- в `reviewRequests` пусто — ревью больше ни от кого не ждут;
- в `latestOpinionatedReviews` (последний апрув или запрос правок каждого ревьювера) есть хотя бы один `APPROVED` и нет `CHANGES_REQUESTED`;
- последний апрув старше `MIN_HOURS` часов (по умолчанию 4).

В тот же GraphQL-запрос добавляются `author { login }` и `latestOpinionatedReviews(first: 20) { nodes { author { login } state submittedAt } }`.

### Формат

Второй блок того же сообщения в Code Review, после «⏰ Ждут ревью»; ждущих ревью нет — в сообщении только он:

```
✅ Одобрены, ждут мержа

• frontend · WEB-25: Форма входа            ← ссылка на PR
  <пинг iRedTea> · одобрен 6 ч назад (апрув: YarikMix)
```

Пингуется автор PR, одобрившие — текстом. Сверху те, кто ждёт дольше. До 20 PR на блок, дальше «…и ещё N».

## Часть 3. Служебные алерты (`scripts/reminders.sh`)

Идут отдельным сообщением в общий топик GitHub (`TELEGRAM_TOPIC_ID`), в тех же запусках, что и напоминания.

### Упавшие запуски

- По каждому репозиторию из списка: `GET /repos/<r>/actions/workflows/automation.yml/runs?status=failure&created=><с>`. У `.github` дополнительно — `reminders.yml`.
- `<с>` — время создания предыдущего успешного запуска `reminders.yml`; его нет — 24 часа назад. Один сбой не повторяется в следующих запусках.
- Считается только `failure`; отменённые (склейка комментариев) — нет.
- В репозитории нет `automation.yml` (404) — пропускается с `::warning::`.

### Срок `ADD_TO_PROJECT_PAT`

- Запрос к API с этим токеном, срок — из заголовка ответа `github-authentication-token-expiration`.
- Осталось 7 дней и меньше — предупреждение с датой. Токен отвергнут (401) — «не работает, карточки не добавляются». Заголовка нет (бессрочный токен) — тишина.
- Проверяется копия секрета в организации; во frontend и backend лежат свои копии — предупреждение напоминает обновить все три.
- Раз в день: cron делится на `0 7 * * *` и `0 12,17 * * *`, проверка токена — только в запуске по первому (`github.event.schedule`) и при ручном запуске.

### Формат

```
🚨 Сбои уведомлений · <пинг YarikMix>
• backend: 2 упавших запуска «Автоматизации» — последний     ← ссылка на запуск
• .github: 1 упавший запуск «Напоминаний о ревью»
🔑 ADD_TO_PROJECT_PAT истекает через 5 дней (2026-10-01). Выпустите новый и обновите секрет в организации, frontend и backend.
```

Сбоев нет и токен в порядке — сообщения нет. Кого пинговать — константа в начале скрипта.

### Изменения в `reminders.yml`

- два cron-выражения вместо одного;
- env: `PAT` (`secrets.ADD_TO_PROJECT_PAT`), `OPS_TOPIC` (`vars.TELEGRAM_TOPIC_ID`), `DAILY` (ручной запуск или утренний cron);
- `permissions`: к `contents: read` добавляется `actions: read`.

### Ошибки

Сбой служебных проверок (API не ответил) не должен глушить напоминания о ревью: проверка пишет `::warning::` и пропускается, дайджест уходит. Отказ Telegram по-прежнему валит job.

## Проверка

**Локально:**

- `tests/telegram.sh` (`REVIEW_WAIT=0`): серия из одного и из нескольких ревью, общий текст ревью считается, промежуток больше порога разрывает серию, чужие ревью не считаются; апрув и правки со строкой комментариев и без; автор PR и бот — тишина; API недоступен — сообщение без числа и `::warning::`; склонение.
- `tests/reminders.sh`: одобрен 4+ часа — в блоке; одобрен недавно, есть `CHANGES_REQUESTED`, кто-то ещё в Reviewers, черновик — нет; оба блока в одном сообщении; только блок одобренных; сортировка и лимит. Служебные: упавшие запуски по репозиториям, окно от предыдущего успешного запуска и запасные 24 часа, 404 пропускается, токен — 8 дней (тишина), 5 дней, 401, без заголовка, `DAILY` выключен; сбой служебного API не мешает дайджесту; запрос покрывает все восемь репозиториев.
- `tests/lint.sh` — без изменений, должен пройти (в том числе `concurrency` в `telegram.yml`).

**На живых событиях:**

| Что | Как | Ожидание |
|---|---|---|
| `figma` подключён | PR с `automation.yml` в `figma` | «⚒️», «🔀», «🎉» в общем топике |
| склейка комментариев | в PR `.github` с этой правкой второй человек оставляет 2 одиночных комментария с паузой меньше 3 минут | один отменённый запуск, одно «💬 … 2 комментария» в Code Review через ~3 минуты |
| одобренные и служебные | после мержа `gh workflow run reminders.yml -f min_hours=0` | запуск зелёный; блок «✅», если есть одобренный PR; в логе виден срок токена |

## Порядок выкатки

1. Подключить `figma` (PR в `figma`).
2. PR в `.github` с частями 0–3; живая проверка склейки; мерж.
3. Ручной запуск `reminders.yml`.

## Вне рамок

- Уведомления об упавшем CI репозиториев (`workflow_run`) — отдельная задача, требует правки файлов-вызовов.
- Комментарии в обсуждении PR вне ревью (`issue_comment`).
- Проверка срока копий `ADD_TO_PROJECT_PAT` во frontend и backend.
- Прямые пуши в `main`, переоткрытие PR, перевод в черновик, снятие ревью.
