# Доработка алертов: описания, force-push, комментарии, кнопки, новые репозитории

Дата: 2026-09-26
Статус: спека

## Зачем

Разбор сообщений бота в топиках GitHub и Code Review за 20–26.09 и список пожеланий команды:

1. Обрезанные описания задач кончаются мусором `â¦` вместо `…`.
2. Markdown и HTML из описаний идут как есть: `**Зачем**`, `**DoR**`, целый тег `<img width="3192" … />`.
3. Force-push после rebase выдаёт всю ветку заново («20 коммитов» дважды за вечер), а в список попал коммит из main (`Merge pull request #2`).
4. infra PR #3 закрылся без алерта. Его закрыл GitHub: после force-push в 20:37:30 у ветки не осталось общей истории с main (`compare` отвечает `No common ancestor`), и `closed` с `head_ref_force_pushed` стоят в таймлайне в одну секунду. На такое закрытие событие `pull_request` не приходит — запуска «Автоматизации» не было.
5. Комментарии под задачами и в обсуждении PR не доходят до чата.
6. Под частью алертов нет кнопок — только ссылка в заголовке.
7. Ментор попросил напоминать о ревью реже: раз в сутки вместо трёх раз в день.
8. О новом репозитории в организации никто не узнаёт, а его нужно подключить к уведомлениям (сегодня так появился `claude-plugins`).

Всё правится в `Cringe-Driven-Development-Team/.github`. Пункт 5 дополнительно требует однострочной правки `automation.yml` в каждом подключённом репозитории.

## Решение по структуре

Логика остаётся inline в `telegram.yml`, как сейчас. Вынос в `scripts/telegram.sh` потребовал бы в каждом событии checkout репозитория `.github` на нужном SHA (`job_workflow_sha`) — лишняя точка отказа и секунды на каждое событие. Тесты уже вытаскивают `run:`-блок через `tests/extract-run.awk`, actionlint прогоняет его через shellcheck.

## Часть 1. Описания задач и комментариев (`telegram.yml`)

Одна функция `quote` превращает текст из GitHub в цитату для Telegram. Используется для описаний задач (создание, правка) и для комментариев (часть 4).

### Порядок обработки

perl запускается с `-CS -Mutf8`: без `-Mutf8` литерал `…` в коде — три отдельных байта, каждый кодируется в UTF-8 заново, отсюда `â¦`.

1. Вырезать `<!-- … -->` и `\r`.
2. Картинки — `<img … src="URL" …>` и `![alt](URL)` — заменить на markdown-ссылку `[🖼 картинка](URL)`: в шаге 7 она станет `<a>`.
3. `<br>` и закрывающие блочные теги (`</p>`, `</div>`, `</summary>`, `</details>`, `</li>`, `</tr>`, `</hN>`) — перевод строки. Остальные HTML-теги — всё, что похоже на `</?буква…>`, — снять, текст внутри оставить. Одиночные `<` и `>` в тексте (`a < b`) не трогаются; `<https://…>` остаётся ссылкой, `<адрес@почта>` — текстом, а тег не схлопывает текст между `<` и `>`, если между ними перевод строки.

Шаги 2–3 не трогают код: `` `…` `` и ```` ```…``` ```` пропускаются как есть (`pulumi/<id>` в коде остаётся).
4. Схлопнуть 3+ переводов строки в 2, обрезать пробелы по краям.
5. Длиннее 700 символов — обрезать до 700 и добавить `…`. Длина считается в символах, не байтах.
6. Экранировать `&`, `<`, `>`.
7. Перевести markdown в HTML Telegram:
   - блок ```` ```…``` ```` → `<pre>`; непарная ```` ``` ```` (отрезана обрезкой) — удаляется;
   - `` `x` `` → `<code>x</code>`; содержимое кода дальше не трогается;
   - `# X` … `###### X` в начале строки → `<b>X</b>`;
   - `**x**` → `<b>x</b>` (пара в пределах строки);
   - `~~x~~` → `<s>x</s>`;
   - `[t](url)` → `<a href="url">t</a>`;
   - `- [ ] ` / `- [x] ` → `☐ ` / `☑ `; `- ` / `* ` в начале строки → `• `.

Курсив (`*x*`, `_x_`) и жирный через `__x__` не переводятся: ломают `snake_case`, `__init__` и списки. Непарные `**` после обрезки остаются как есть.

Результат оборачивается в `<blockquote expandable>`, как сейчас.

### Страховка от кривой разметки

Если Telegram отвечает `can't parse entities`, то же сообщение отправляется повторно без цитаты, в лог — `::warning::`. Остальные отказы валят job, как раньше.

## Часть 2. Force-push (`telegram.yml`)

### Коммиты

Для пуша с `forced == true` список коммитов берётся не из payload (там до 20 коммитов и вся переписанная ветка), а из API:

- `AFTER_LIST` — `GET /repos/R/compare/<default>...<after>`: коммиты ветки поверх ветки по умолчанию (`github.event.repository.default_branch`), до 250;
- `BEFORE_LIST` — `GET /repos/R/compare/<default>...<before>`: старая версия ветки;
- новые — коммиты `AFTER_LIST`, чьих заголовков (первая строка сообщения) нет в `BEFORE_LIST`.

### Сообщение

```
⚠️ force-push · infra · task-infra-1           ← ветка ссылкой, как сейчас
ветка переписана: 20 коммитов поверх main, новых — 1
• 1571532 fix: замечания ревью F2–F7
iRedTea
[Ветка целиком]                                ← compare/<default>...<ветка>
```

- новых нет — вторая строка `ветка переписана: 20 коммитов поверх main, новых коммитов нет`, списка нет;
- поверх main ничего не осталось — `ветка сброшена до main`, списка нет;
- до 10 новых коммитов в списке, дальше `…и ещё N`, как сейчас;
- `BEFORE_LIST` не получен (старый коммит недоступен) — все коммиты ветки считаются новыми, вторая строка `ветка переписана: N коммитов поверх main`;
- у ветки нет общей истории с веткой по умолчанию (`compare` отвечает 404 `No common ancestor`) — вторая строка `у ветки нет общей истории с main`, коммиты — из payload, как у обычного пуша (`distinct`), кнопка на `compare` из события;
- `AFTER_LIST` не получен по другой причине — поведение как сейчас (payload, `distinct`, кнопка на `compare`, заголовок `⚠️ N коммитов (force-push)`), в лог `::warning::`.

Обычный пуш (не force) не меняется.

## Часть 3. PR, закрытый GitHub после force-push (`telegram.yml`)

После сообщения о force-push:

1. `GET /repos/R/pulls?state=closed&head=<владелец>:<ветка>&sort=updated&direction=desc&per_page=5` — закрытые PR ветки.
2. Кандидаты: `merged_at == null` и `closed_at` совпадает с моментом пуша (`repository.pushed_at`, ±10 секунд) — так корректирующий force-push в те же 5 минут не берёт на себя чужое закрытие; `pushed_at` пуст или не число — запасное правило, как раньше: `closed_at` не раньше 5 минут назад.
3. Для кандидата `GET /repos/R/issues/N/events`: закрыл GitHub, если есть `closed` и `head_ref_force_pushed` с одинаковым `created_at`. Иначе PR закрыл человек — об этом уже пришёл алерт `pull_request: closed`, молчим.
4. Сообщение в общий топик:

```
🚫 PR закрыт без мержа · infra
Task infra 1: pulumi ready                     ← ссылка на PR
автор: <пинг iRedTea>
GitHub закрыл PR после force-push: у ветки не осталось изменений или общей истории с main
[Открыть PR]
```

API недоступен — без сообщения, `::warning::` в лог.

## Часть 4. Комментарии (`telegram.yml`)

Новое событие `issue_comment: created`. Правки и удаления комментариев не сообщаются.

### Молчим

- комментарий оставил бот (`comment.user.type == Bot`).

### Под задачей — топик GitHub

```
💬 Комментарий · infra
#5 Bootstrap-стек для бакета стейта Pulumi     ← ссылка на комментарий
от: YarikMix · для: <пинг исполнителей и автора задачи, кроме автора комментария>
┃ цитата комментария (часть 1)
[Открыть комментарий]
```

Пинговать некого (пишет единственный участник) — строка только `от: …`, без `для:`.

### В обсуждении PR — топик Code Review

Событие `issue_comment` с `issue.pull_request`. Inline-комментарии ревью сюда не относятся — они идут через `pull_request_review`, как раньше.

```
💬 Комментарий к PR · backend
API-16: Реализовать API ручки пользователей    ← ссылка на комментарий
от: blackHATred · для: <пинг>
┃ цитата
[Открыть комментарий]
```

- пишет не автор PR — пингуется автор PR;
- пишет автор PR — пингуются запрошенные ревьюверы (`GET /repos/R/pulls/N`, `requested_reviewers`); их нет или API недоступен — без пинга.

Серии комментариев не склеиваются: в отличие от ревью, обсуждение редко идёт очередью из одиночных событий.

### Ограничение

События `issue_comment`, как и `issues`, всегда берут workflow из ветки по умолчанию: проверить их можно только после мержа.

## Часть 6. Напоминания раз в сутки (`reminders.yml`, `scripts/reminders.sh`)

Расписание не меняется: 10:00, 15:00, 20:00 МСК. Дайджест («⏰ Ждут ревью», «✅ Одобрены, ждут мержа», предупреждение об отключении cron) уходит только при `DAILY=true` — в утреннем запуске и при ручном. В 15:00 и 20:00 — только служебные проверки. `MIN_HOURS` остаётся 4.

## Часть 7. Новый репозиторий (`scripts/reminders.sh`)

В каждом запуске, в блоке служебных проверок (до дайджеста):

1. `GET /orgs/Cringe-Driven-Development-Team/repos` (с пагинацией).
2. Новые — `created_at` позже `SINCE` (последний успешный запуск напоминаний; та же отсечка, что у упавших запусков, поэтому сообщение не повторяется).
3. Для каждого нового — проверки подключения:
   - есть ли `.github/workflows/automation.yml` (`GET /repos/R/contents/…`, 404 — нет);
   - есть ли репозиторий в `REPOS`.
4. Отдельное сообщение на каждый новый репозиторий в общий топик (`OPS_TOPIC`):

```
🆕 Новый репозиторий · claude-plugins          ← ссылка на репозиторий
<описание, если есть>
⚠️ не подключён: нет automation.yml, нет в REPOS (scripts/reminders.sh)
[Открыть репозиторий]
```

Строка `не подключён` — только если чего-то нет; перечисляется только отсутствующее. Кто создал репозиторий, API без прав администратора не отдаёт.

API недоступен — `::warning::` в лог, job не падает, как у остальных служебных проверок.

`GITHUB_TOKEN` видит только публичные репозитории; сейчас все репозитории организации публичные.

Кнопка требует `reply_markup` в `send` скрипта — сейчас там кнопок нет; добавляется необязательный третий аргумент.

## Тесты

`tests/telegram.sh`:

- описание: жирный, код, блок кода, ссылка, картинка `<img>` и `![]()`, `<details>`, чекбоксы, обрезка кириллицы (конец — `…`, нет `â`), непарные `**` и ```` ``` ```` после обрезки;
- повторная отправка без цитаты при `can't parse entities`;
- force-push: rebase без новых коммитов, rebase с новым коммитом, сброс до main, недоступный `before`, недоступный API;
- автозакрытый PR: закрыт GitHub — сообщение; закрыт человеком — нет; влит — нет;
- комментарии: под задачей, в PR от ревьювера, в PR от автора, от бота;
- кнопки у всех алертов из таблицы.

Заглушка `gh` — по образцу тестов повторного ревью.

`tests/reminders.sh`:

- `DAILY=false` — дайджеста нет, служебные проверки есть;
- новый подключённый репозиторий, новый неподключённый, старый, недоступный API.

## Раскатка

1. Ветка `feature/alerts-polish` → PR в `.github`: спека, план, реализация. Пуши, PR и ревью проверяются прямо в PR — репозиторий вызывает свои workflow из той же ветки.
2. В шаблон `automation.yml` (README) и в `automation.yml` самого `.github` добавляется:
   ```yaml
   issue_comment:
     types: [created]
   ```
3. После мержа — такой же PR в `automation.yml` у docs, static, infra, react, figma, frontend и backend. Пока его нет, в репозитории нет алертов о комментариях; остальное работает. Эти PR открываются после отдельного подтверждения.
