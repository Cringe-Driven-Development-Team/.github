# Статусы закрытых задач и выпусков frontend

Дата: 2026-11-04. Состояние: согласована пользователем; реализация подготовлена, внешнее подключение ожидается.

## Цель и согласованное поведение

На общей доске Scrumban №1 закрытие фронтовой issue не должно означать,
что её изменения уже работают на проде. Для остальных репозиториев закрытие
по-прежнему означает `Done`. Issues продолжают закрываться при мерже PR.

Пользователь согласовал:

| Событие | Статус карточки |
| --- | --- |
| Задача frontend закрыта мержем PR; сборка и публикация ещё не завершены | `Ready for build` |
| Оба артефакта выпуска опубликованы и проверены: статика S3 и образ BFF GHCR | `Ready for release` |
| Выпуск успешно выкачен на прод | `Done` |
| Фронтовая задача закрыта вручную без закрывающего PR либо как `not planned` | `Done` |
| Закрыта задача любого другого репозитория общей доски | `Done` |

Сбой сборки/публикации оставляет `Ready for build`. Сбой выкатки оставляет
`Ready for release`, если эта задача ещё ни разу не попадала в успешную выкатку.
Существующая семантика rollback сохраняется: уже выкаченные задачи не возвращаются
назад по колонкам при откате на старый выпуск.

## Подходы

**Выбранный пользователем: дополнить существующую общую автоматизацию и Board.**
Общий обработчик закрытия определяет начальный статус по репозиторию и причине
закрытия; Board продвигает фронтовые задачи по проверенным выпускам. Затем
отключается общее встроенное правило `Item closed`. Используются существующие
callers и ADD_TO_PROJECT_PAT, без нового сервиса и без разделения доски.

Альтернатива — перенести все изменения карточек в webhook-сервис. Это потребовало
бы дать ему права записи Projects и перенести сверку выпусков. Для данного
исправления не выбрана: пользователь согласовал существующую автоматизацию.

Оставить встроенный `Item closed` и ускорить последующий откат статуса недостаточно:
ложный `Done` всё равно возникал бы. Фильтр по репозиторию для этого встроенного
workflow не подтверждён и не является предпосылкой решения.

## Общий обработчик закрытия

Добавить обработку `issues.closed` в существующую автоматизацию `.github`.
Перед изменением читать текущее состояние issue и её актуальное событие закрытия;
запоздавший payload сам по себе не является основанием для записи.

Согласованная классификация: релизный процесс определяется точным репозиторием
`Cringe-Driven-Development-Team/frontend` и закрытием мержем PR этого репозитория
в его default branch. Заголовки `Frontend.`/`BFF.` не используются как технический
признак: переименование issue не должно выключать автоматику. Остальные закрытия
во frontend, включая ручные и `not planned`, получают `Done`.

Обрабатываются только issue-карточки существующей доски №1. Другие проекты и
PR-карточки не затрагиваются. Issue вне этой доски не добавляется при закрытии.
Нет доступа к Project или нужного Status option — видимая ошибка, без успешного
отчёта о несостоявшемся изменении. Уже нужное значение не записывается повторно.

Для закрытой мержем фронтовой issue обработчик задаёт `Ready for build`.
Он не возвращает карточку назад, если Board уже подтвердил публикацию/выкатку
для того же закрывающего PR. После переоткрытия и нового закрытия используется
новый цикл задачи, а не устаревшее событие. Перед записью нужна повторная проверка
актуальности закрытия и статуса.

Нельзя помещать все независимые `issues.closed` в одну concurrency-группу,
которая вытесняет ожидающие запуски: закрытие второй задачи не должно терять
обновление первой. Конкретный способ согласования записей выбирается при плане;
обязательный результат — отсутствие пропусков и регрессии релизного статуса.
Повторное чтение перед mutation само по себе не является блокировкой: план должен
предусмотреть согласование или исправление пересекающихся записей, а тест —
воспроизвести запись Board между чтением и записью обработчика закрытия.

## Изменения frontend Board

Убрать ожидание встроенного `Done` и требование его updatedAt после ClosedEvent.
Доказательства закрытия мержем, принадлежности PR выпуску и успешных Deployments
сохраняются. `Ready for build` становится обычным входом в автоматические переходы.

Для закрытой мержем задачи из frontend фактический выпуск имеет приоритет над
оставшимся рабочим статусом (`In review`, `Ready for test`, `In testing` и т. п.).
Если первоначальный обработчик ещё не выполнился, Board всё равно выставляет
`Ready for release` по публикации или `Done` по выкатке. Это согласованное
изменение прежней защиты ручных статусов, а не снятие защиты открытых задач.

Board не меняет открытые/переоткрытые задачи, задачи других репозиториев,
ручные закрытия и `not planned`. Не требуется сначала искусственно выставлять
`Ready for build`, если к моменту сверки уже подтверждён более поздний этап.
Поддержка существующих закрытых карточек в `Done` сохраняется: история выпусков
определяет, должны ли они ожидать выкатки.

Проверки непосредственно перед записью сохраняются: переоткрытая задача не
получает устаревший статус, а успешный CD во время сверки учитывается. Нужен тест
на совместную работу нового обработчика закрытия и Board, а не только на каждый
из них отдельно.

## Границы и решения автора проекта спецификации

- В работе два репозитория: `.github` (общий обработчик, тесты, CONTRIBUTING,
  описание автоматики) и `frontend` (Board, связанные тесты, docs/release.md).
  Caller-файлы других репозиториев меняются только если их проверка выявит
  отсутствие нужного события/версии общего workflow.
- Классификация по репозиторию вместо префикса заголовка и отсутствие добавления
  чужих карточек при закрытии вошли в согласованную спецификацию.
- Не менять Telegram, вебхуки, порядок CI/CD, merge queue, права мержа и спринты.
- Не добавлять новые колонки, зависимости, поддержку старых клиентов, сервисы,
  миграционные флаги или двойную запись на период перехода.
- Ускорение полного обхода Board не входит в эту работу. Переходы остаются
  асинхронными: краткое ожидание рабочего статуса или `Ready for build` допустимо,
  ложный `Done` после нового мержа при выключенном Item closed — нет.
- Код не способен гарантировать мгновенное обновление карточки при задержке
  GitHub Actions или недоступности API. Ошибки видны в Actions, повтор допустим.

## Подключение и проверка

Сначала подготовить и проверить обе реализации. При подключении проверить
фактические встроенные workflows проекта: `Pull request merged`, `Item reopened`,
`Pull request linked to issue` и `Auto-close issue`. Убедиться, что ни один другой
обработчик не выставляет `Done` связанной issue при мерже. Правила PR-карточек
и обычного переоткрытия менять без такой причины не требуется.

После готовности новой автоматики отключить `Item closed` №7, проверить сохранение
настройки и выполнить интеграционную приёмку. Это обычное изменение общей настройки,
без требования непрерывного перехода или отдельного legacy-режима.

Обязательные локальные сценарии:

1. Frontend merge закрывает issue → `Ready for build`, даже из `In review`.
2. Проверенная публикация → `Ready for release`; неуспешная публикация не продвигает.
3. Успешный production → `Done`; ошибка CD не продвигает; rollback не регрессирует.
4. Backend, infra и другие подключённые репозитории: закрытие → `Done`.
5. Frontend manual close / not planned → `Done`; Board их затем не переписывает.
6. Повтор события не даёт лишней записи; запоздавшее закрытие после публикации
   и после выкатки не возвращает `Ready for build`.
7. Переоткрытие до обработки и новый цикл закрытия учитываются; переименование
   заголовка не исключает фронтовую задачу из релизного процесса.
8. Два закрытия подряд не теряются; concurrent Board и close не оставляют
   регрессировавший статус. Недоступность API даёт ошибку с возможностью повтора.
9. Существующая межрепозиторная страховка закрытия и добавление новых issue
   продолжают работать. Другие проекты не меняются.

Живая приёмка после подключения: новые закрытия frontend и backend, публикация
фронтового выпуска, значения Status через API, отсутствие `Done` до выкатки.
Реальную выкатку для приёмки не запускать автоматически; использовать следующую
согласованную выкатку либо отдельно получить поручение на запуск CD. Локальный
тест перехода в Done обязателен независимо от наличия живой выкатки.

## Следующий шаг

После согласования этой спецификации — план реализации. Перед реализацией готового
плана пользователь выбирает executing-plans либо subagent-driven-development;
выбор из прошлой сессии для другого плана сюда не переносится.
