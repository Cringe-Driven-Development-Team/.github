# Сервис уведомлений GitHub и Apidog — дизайн

Задача: [.github#20](https://github.com/Cringe-Driven-Development-Team/.github/issues/20). Инфраструктурная зависимость [infra#54](https://github.com/Cringe-Driven-Development-Team/infra/issues/54) выполнена. Этот документ описывает сервис и его включение; требования задачи имеют приоритет при расхождении.

## Зачем и границы

Событийные сообщения Telegram сейчас создаёт reusable workflow `.github/workflows/telegram.yml` в каждом репозитории. Новая служба на auxiliary VPS должна принимать один webhook организации GitHub и уведомления Apidog, сохранять их до отправки и переживать временные сбои Telegram. Чат `-1003713420351`: GitHub — тема `26`, Code Review — `1513`; тема Apidog задаётся переменной. Существующие релизные темы `3375` и `3377` обслуживают отдельные workflow.

В задачу входят события `push`, `issues`, `issue_comment`, `pull_request`, `pull_request_review` и выбранные уведомления Apidog. Автоматизация доски, расписание напоминаний, дайджесты, `course-sync` и специальные сообщения о выкатках остаются в Actions. Их код и настройки не переносим. Изменение конфигурации этих систем ради отключения событийной отправки допускается только в точке переключения.

Успех: после переключения подтверждённое событие создаёт нужные сообщения в правильных темах, повтор доставки GitHub не создаёт второго сообщения, сбой Telegram не теряет принятую доставку, а восстановленная SQLite сохраняет очередь и ключи дедупликации. Допустима модель доставки **не менее одного раза**: при аварии между успешным ответом Telegram и записью результата в SQLite возможно повторное сообщение. Это окно невозможно устранить без идемпотентного API Telegram; оператор видит такую доставку в журнале.

## Решения исполнителя

- Код — TypeScript на Bun 1.4.4 и Hono; исходящие HTTP-запросы — `fetch`; хранилище — `bun:sqlite` в `/data/queue.sqlite`. Версию зависимостей фиксирует `bun.lock`, Docker образ имеет неизменяемый SHA тег. Один экземпляр приложения и один worker на одной VPS.
- `GET /health` проверяет, что процесс запущен и SQLite доступна; не зависит от Telegram. `POST /webhooks/github` и `POST /webhooks/apidog` принимают только JSON размером до 1 МиБ. Неизвестный путь — 404, неподдерживаемый тип события — 2xx после проверки подписи без Telegram сообщения. Запрос сверх лимита — 413; плохой JSON — 400; неверная или отсутствующая подпись — 401; ошибка записи в SQLite — 503. Для GitHub ответ 2xx даётся после транзакционного сохранения, в пределах 10 секунд.
- GitHub: HMAC SHA-256 от **исходных байтов** тела, заголовок `X-Hub-Signature-256`, сравнение постоянного времени. Обязательны `X-GitHub-Delivery` и `X-GitHub-Event`. Уникальный ключ `(source, delivery_id)` в SQLite; повтор с тем же ID отвечает 2xx без новых заданий. Повтор с тем же ID и другим телом получает 409 и журналируется.
- Apidog: notification target с включённой `Signature Auth` и отдельным ключом. Документация Apidog указывает HMAC SHA-1 с префиксом `sha1=`, но не фиксирует в тексте имя HTTP-заголовка. Поэтому имя заголовка задаётся `APIDOG_SIGNATURE_HEADER` и сверяется по настоящей тестовой доставке до боевого включения. HMAC также проверяется по исходным байтам. Если payload содержит устойчивый ID уведомления, используем его; иначе ключом дедупликации становится SHA-256 тела в пятиминутном окне. Это может подавить две дословно одинаковые легитимные доставки в этом окне; решение и наблюдение за ним фиксируются в runbook.
- GitHub API нужен для дополнений, которых нет в webhook payload: сравнение после force push, история ревью, inline комментарии и запрошенные ревьюверы. `GITHUB_API_TOKEN` хранится в Vault, имеет только read доступ к обслуживаемым репозиториям. Недоступность API не должна отменять уже принятое событие: отправляем базовое сообщение и записываем предупреждение там, где старый workflow так уже делает.
- Все значения `GITHUB_WEBHOOK_SECRET`, `APIDOG_SIGNATURE_KEY`, `GITHUB_API_TOKEN`, `TELEGRAM_BOT_TOKEN`, chat/topic IDs и карта GitHub→Telegram приходят из `vault_hooks_env`; секреты не попадают в ответы и логи. Наличие критичных переменных проверяется при старте. Для локального теста используются ненастоящие значения.

## Очередь и отправка

В SQLite храним принятый payload, источник, ID доставки, hash тела, время приёма и состояние подготовки; отдельно — исходящие Telegram сообщения со статусом, номером попытки, временем следующей попытки, последней безопасной диагностикой и `message_id` после успеха. Преобразование входящего события в 0–N исходящих строк выполняется транзакционно. Уникальный ключ исходящей строки — тип источника (`delivery` или `review_group`), его ID и порядковый номер: перезапуск подготовки не создаёт новых сообщений.

Worker берёт готовые строки с ограничением числа одновременных отправок, ставит lease с истечением, вызывает Telegram `sendMessage`, затем сохраняет успех. Сетевой сбой и 5xx — экспоненциальный backoff с jitter; 429 — `retry_after` плюс небольшой запас; постоянный 4xx (кроме 429) — состояние `failed`, видимое оператору и доступное для ручного повторного запуска после исправления. В рестарте истёкший lease снова доступен. `retry` CLI повторяет failed записи без изменения ключей дедупликации. Payload и ответы Telegram не выводим в журналы целиком; логируем ID доставки, тип события, попытку, HTTP статус и код ошибки.

Для `pull_request_review:submitted` с `state=commented` объединяем сообщения одного `repo + PR + reviewer`: срок готовности — 180 секунд после последнего комментария. Новые комментарии продлевают срок, перезапуск процесса его сохраняет. `approved` и `changes_requested` выходят сразу и учитывают уже готовую серию комментариев без двойного сообщения. Событие открытия PR может породить карточку в GitHub и отдельный запрос ревью в Code Review; обе строки имеют независимые статусы отправки.

## Содержание сообщений

Эталон — `.github/workflows/telegram.yml` и `tests/telegram.sh`. Сохраняем существующие эмодзи и короткие заголовки, ссылки, кнопки, упоминания из `TELEGRAM_USER_MAP`, поведение черновиков, тишину для ботов и `<!-- auto -->`, фильтр ранней правки issue, фильтр неуникальных коммитов и отдельную тему ревью. `push` включает максимум 10 коммитов и остаток счётчиком. Для force push и повторного ревью используем GitHub API с теми же мягкими fallback, что сейчас. HTML и URL экранируются, цитата описания ограничена 700 символами, всё сообщение — ниже лимита Telegram 4096 символов. На отказ Telegram из-за разметки цитаты повторяем карточку без цитаты, как в текущем workflow.

Apidog направляется только в настраиваемую тему. Выбираем изменения endpoint, schema и документа, а также завершение автоматических тестов по возможностям проекта; отправляем источник, действие, объект и ссылку, если она есть в payload. Неизвестный тип, неполные поля и отсутствие URL дают короткую безопасную карточку с названием события без выдуманной ссылки. Формат полей окончательно закрепляется обезличенной fixture из тестовой доставки Apidog до включения реальных уведомлений.

## Снимок и восстановление

CLI сервиса `bun run src/cli.ts snapshot --output /data/snapshots/queue.sqlite` подключается к работающей БД, делает SQLite `VACUUM INTO` во временный файл в том же каталоге, проверяет `PRAGMA integrity_check`, синхронизирует файл и каталог и атомарно заменяет готовый снимок. При ошибке предыдущий снимок остаётся, команда возвращает ненулевой код. Прямое копирование `/data/queue.sqlite` и её `-wal` во время работы резервной копией не считается.

В infra unit Restic перед своим `backup` вызывает CLI внутри контейнера через `docker compose exec -T hooks`; при ошибке создания снимка бэкап считается неуспешным. Restic сохраняет готовый `/var/lib/docker/volumes/hooks_hooks_data/_data/snapshots/queue.sqlite`, нужные тома Caddy и `/opt/hooks`, но исключает работающую БД. Перед переключением выполняем backup и изолированное restore при отключённом Telegram: `integrity_check = ok`, ожидающие и обработанные строки и ID доставок на месте, повтор старого ID не добавляет событие. Этот результат записываем в runbook/PR. Изменение infra оформляем отдельной sub-issue к .github#20 и вливаем до PR, закрывающего родителя.

## Переключение и откат

Новый образ сначала разворачивается с остановленной отправкой Telegram; проверяются `/health`, подписи, тестовые GitHub/Apidog POST, маршрут Caddy, изолированный тестовый чат и восстановление. Затем настраивается organization webhook GitHub на `https://hooks.cellestial.ru/webhooks/github` и Apidog notification target на `/webhooks/apidog`; сервис принимает события в очередь, но не отправляет их в боевой чат. Старый событийный workflow пока работает. На переключении отдельным организационным флагом выключаем **только** job событийного `telegram.yml`, дожидаемся завершения уже запущенных jobs, фиксируем границу старых доставок и запускаем worker для новых. События пограничного периода сверяем по GitHub Recent Deliveries и Actions, чтобы не отправить повторно; их можно вручную повторить из очереди. После этого проверяем один event → одно сообщение, темы и оставшиеся job доски и напоминаний. Откат: останавливаем worker, возвращаем флаг событийного workflow, проверяем новые доставки; очередь не удаляем и не воспроизводим её автоматически в старый канал.

Точки переключения и восстановления — операционные действия по runbook. До них не отключаем `telegram.yml` и не подключаем боевой токен Telegram к работающему worker.

## Проверки и источники

`bun test`, `bunx tsc --noEmit`, Docker build, действующие shell тесты и CI обязательны. Тесты охватывают HMAC и исходные байты, неверный размер и JSON, duplicate delivery, рестарт, 429/5xx/4xx, HTML и лимиты, маршрутизацию, объединение ревью и восстановление снимка. Fixtures GitHub берём из обезличенных реальных webhook доставок либо официальных примеров; fixture Apidog — из тестовой доставки проекта, без ключей и личных данных. Для живой приёмки используем отдельную тему или тестовый чат, чтобы не создать двойную рассылку.
