# Задачи фронта и бэка — в нашей организации

Дата: 2026-09-29
Статус: спека

## Зачем

Код продукта лежит в курсовых репозиториях чужих организаций, правила там задают менторы:

- frontend — `frontend-park-mail-ru/2026_2_Cringe_Driven_Development`;
- backend — `go-park-mail-ru/2026_2_Cringe_Driven_Development`.

В main обоих — только через PR с апрувом ментора, мержат менторы. Задачи фронта и бэка сейчас заводятся там же, а доска Scrumban (`https://github.com/orgs/Cringe-Driven-Development-Team/projects/1`), бот и спринты живут в `Cringe-Driven-Development-Team`.

Решение: код остаётся в курсовых репозиториях, задачи ведём в нашей организации. PR закрывает задачу ключевым словом с полным путём — `Closes Cringe-Driven-Development-Team/frontend#N`. Цена: в курсовых репозиториях задач не будет; если менторы ждут их там, это согласуется отдельно (см. «Issues в курсовых репозиториях»).

## Репозитории задач

`Cringe-Driven-Development-Team/frontend` и `Cringe-Driven-Development-Team/backend`, публичные, как остальные репозитории организации. Содержимое:

- `.github/workflows/automation.yml` — шаблон из README `.github` без изменений: задачи попадают на доску (job `board`) и в чат (job `telegram`);
- `README.md` — одна строка: «Задачи фронтенда (бэкенда). Код — в <ссылка на курсовой репозиторий>».

Секреты `TELEGRAM_BOT_TOKEN`, `ADD_TO_PROJECT_PAT` и переменные `TELEGRAM_*` заданы на уровне организации с видимостью `all` (проверено 2026-09-28) — новые репозитории получают их без настройки.

Подпись стороны в сообщениях бота, напоминаниях и итогах спринта — общее правило «имя репозитория» (`side` в `telegram.yml`, `scripts/reminders.sh`, `scripts/sprint.sh`): задачи из новых репозиториев подписываются `frontend` и `backend`, как сейчас задачи из курсовых. Правило не меняется.

### Как завести задачу

Основной способ — с доски: `+ Add item` → ввести `#` → выбрать `frontend` или `backend` → `Create new issue`. Получается настоящая задача в репозитории: с номером, веткой и связью с PR; бот о ней сообщает. Созданная в колонке `Ready` получает статус `Ready`. Подставляется ли `Sprint` из фильтра вида `sprint:@current` — проверяется на шаге «Проверка» раскатки.

Текст без `#` создаёт draft issue — карточку только на доске: без репозитория и номера, без ветки, PR её не закроет, бот о ней не узнает. В README курсовых репозиториев об этом — отдельное предупреждение.

## Закрытие задачи мержем

### Ключевое слово

В описании PR в курсовом репозитории — всегда строка `Closes Cringe-Driven-Development-Team/frontend#N` (или `backend#N`). GitHub показывает связь в блоке `Development` и закрывает задачу при мерже в ветку по умолчанию — если срабатывает между организациями. Мержат менторы, у которых нет прав на запись в наши репозитории; закроет ли GitHub задачу в этом случае — неизвестно и нашими силами не проверяется. Поэтому — страховка.

### Страховка: job `close` в `add-to-project.yml`

Курсовые репозитории уже вызывают `Cringe-Driven-Development-Team/.github/.github/workflows/add-to-project.yml@main` с секретом `ADD_TO_PROJECT_PAT` и подписаны на `pull_request: closed`. Второй job в этом workflow работает во всех подключённых репозиториях без PR в курсовые.

Скрипт — в блоке `run: |` самого job, как в `telegram.yml`: reusable workflow выполняется в репозитории-вызывателе, `scripts/` из `.github` там нет.

**Когда:** `github.event_name == 'pull_request'`, `action == 'closed'`, `pull_request.merged == true`, `pull_request.base.ref == repository.default_branch`. Иначе job пропускается (`if:` на уровне job). Мерж не в ветку по умолчанию не закрывает задачи — как у GitHub.

**Что ищет:** в заголовке и описании PR — ключевое слово, необязательное двоеточие, пробелы и полная ссылка на задачу нашей организации:

```
\b(close[sd]?|fix(e[sd])?|resolve[sd]?):?\s+Cringe-Driven-Development-Team/([A-Za-z0-9._-]+)#([0-9]+)\b
```

без учёта регистра. Любой репозиторий организации, не только `frontend`/`backend`. Короткие `#N` и ссылки на другие организации пропускаются — их обрабатывает GitHub. Повторы одной задачи схлопываются.

**Что делает** для каждой найденной задачи `<repo>#<N>` через `ADD_TO_PROJECT_PAT`:

1. `GET repos/Cringe-Driven-Development-Team/<repo>/issues/<N>`. Это PR (есть поле `pull_request`) — пропуск. Закрыта — пропуск: её закрыл GitHub или предыдущий запуск.
2. Комментарий `<!-- auto -->Закрыта мержем <ссылка на PR>`.
3. `PATCH … state=closed, state_reason=completed`.

Порядок относительно закрытия самим GitHub не важен: кто первый, тот и закрыл, второй видит закрытую задачу.

**Ошибки:** PAT пуст, у него нет прав, задачи нет, API недоступен — `::error::` с текстом «не закрыл <repo>#<N>: <ответ gh>», обработка остальных задач продолжается, код выхода ≠ 0. Молча оставшаяся открытой задача хуже упавшего job; падение попадает в «🚨 Сбои уведомлений» (`scripts/reminders.sh` смотрит упавшие запуски «Автоматизации» во всех репозиториях из `REPOS`).

**Права PAT:** закрытие и комментарий требуют записи в задачи репозиториев организации — у fine-grained токена `Issues: Read and write` на репозитории `Cringe-Driven-Development-Team`, у classic — `public_repo`. Сейчас токен точно умеет писать на доску, про задачи — неизвестно. Проверить и при необходимости расширить — YarikMix (владелец токена), до раскатки. Копии секрета в курсовых репозиториях — тот же токен.

### Автокомментарии не шумят в чате

Комментарий от PAT — от пользователя, а не от бота: `telegram.yml` прислал бы «💬 Комментарий» с пингом исполнителей. Поэтому в `issue_comment:created` рядом с пропуском комментариев ботов — пропуск комментариев, которые начинаются с `<!-- auto -->`. Тот же маркер у комментариев переноса (см. «Перенос»). Закрытие задачи — событие `issues: closed`, о нём бот пишет «✅ Задача закрыта», как сейчас; автором действия при закрытии страховкой будет владелец PAT.

## Перенос открытых задач

Transfer issue между организациями GitHub не умеет — задачи копируются. Одноразовый скрипт, запускается локально, в `.github` не коммитится (живёт в плане).

**Что переносится:** все открытые задачи курсовых репозиториев — на 2026-09-28 11 во frontend и 2 в backend (12 на доске со `Status=Ready`, `Sprint=Sprint 3`; frontend#27 на доске нет). Закрытые остаются на месте как история. Открытых PR в курсовых репозиториях нет — чинить ссылки `Closes #N` не нужно.

**Режимы:** `--dry-run` (по умолчанию) печатает таблицу «старая задача → репозиторий, заголовок, исполнители, поля доски» и предупреждения; перенос — только с явным флагом, после «да» пользователя по таблице.

**Для каждой задачи**, по возрастанию старого номера (порядок номеров сохраняется):

1. Уже перенесена — пропуск. Признак — в целевом репозитории есть задача с `Перенесено из <старая ссылка>` в описании; тогда шаги 2–3 пропускаются, 4–6 выполняются, если не выполнены (повторный запуск после сбоя доделывает начатое).
2. Создать задачу в `frontend`/`backend`: тот же заголовок и исполнители; описание — старое, короткие `#N` заменены на `<курсовой репозиторий>#N` (они указывают на курсовые задачи и PR), в конце — строка `Перенесено из <старая ссылка>`. Исполнитель без доступа к нашей организации — предупреждение в dry-run, при переносе он пропускается.
3. Добавить на доску и выставить все заданные у старой карточки пользовательские поля (single select, iteration, number, date). Старой карточки нет — новая добавляется без полей.
4. Комментарий к старой задаче: `<!-- auto -->Перенесено в Cringe-Driven-Development-Team/<repo>#<N>`.
5. Закрыть старую как `not_planned`.
6. Удалить старую карточку с доски — иначе в итогах спринта она посчиталась бы сделанной.

**Шум:** бот сообщит о каждой новой и каждой закрытой задаче — около 26 сообщений в топик GitHub (пользователь согласен). Комментарии с маркером молчат. Команду предупреждаем заранее сообщением в чате с коротким «как теперь заводить и закрывать задачи».

## Изменения в `.github`

- `.github/workflows/add-to-project.yml` — job `close` (см. «Страховка»).
- `.github/workflows/telegram.yml` — пропуск комментариев с `<!-- auto -->`.
- `tests/extract-run.awk` — необязательный `-v n=N`: тело N-го блока `run: |` (по умолчанию первого). Существующие вызовы не меняются.
- `tests/close.sh` — тесты job `close` (см. «Тесты»); `tests/telegram.sh` — случай маркера.
- `scripts/reminders.sh` — `REPOS` += `Cringe-Driven-Development-Team/frontend`, `Cringe-Driven-Development-Team/backend`. Курсовые остаются: по ним идут PR, дайджест ревью и сбои «Автоматизации».
- `README.md` — где живут задачи, как завести с доски, строка `Closes …` в PR, что делает страховка и какие права нужны `ADD_TO_PROJECT_PAT`.

## README курсовых репозиториев

Раздел «Как работать с задачами» во frontend и backend описывает старую схему («задача заводится issue в той репе, где будет код», `Closes #<номер>`). Переписывается PR в каждый курсовой репозиторий (апрув и мерж — менторы):

- задачи — в `Cringe-Driven-Development-Team/frontend` / `backend`, заводятся с доски через `#`; предупреждение про draft issue;
- в описании PR — **всегда** `Closes Cringe-Driven-Development-Team/frontend#N`;
- ветка `web-<N>`, заголовок PR `WEB-<N>: …` — N из нашего репозитория;
- как создать ветку и нужен ли ручной перевод в `In review` — по итогам шага «Проверка»: если «Create a branch for this issue» не умеет репозиторий другой организации — `git fetch && git switch -c web-<N> origin/main`; если PR не связывается с задачей — `In review` руками.

Локальная ветка `web-23` с незакоммиченной правкой README во `frontend` не трогается: правка — отдельной веткой от `origin/main`.

## Issues в курсовых репозиториях

После согласования с менторами Issues выключаются в настройках двух курсовых репозиториев (`has_issues=false`); остальные репозитории организаций менторов не затрагиваются. Следствие: все задачи этих репозиториев, включая 18 закрытых карточек прошлых спринтов на доске, скрываются — ссылки отдают 404, карточки не открываются; включение обратно всё возвращает. Комментарии в PR и события `issue_comment` по PR работают. Шаг ручной, в код не входит; пока Issues включены, случайно заведённая там задача переносится руками.

## Тесты (`tests/close.sh`)

По образцу `tests/telegram.sh`: скрипт job `close` вынимается `extract-run.awk -v n=2`, `gh` — заглушка с ответами из env и журналом запросов.

- мерж в ветку по умолчанию, `Closes Cringe-Driven-Development-Team/frontend#5`, задача открыта → комментарий с маркером и ссылкой на PR, затем закрытие с `state_reason=completed`;
- задача уже закрыта → ни комментария, ни закрытия;
- номер указывает на PR → пропуск;
- `Fixes`, `resolves:`, `CLOSES`; ссылка в заголовке и в описании; одна задача дважды → каждая закрывается ровно один раз;
- несколько задач в разных репозиториях → все;
- `#5` без префикса, ссылка на другую организацию, слово без ключевого (`see Cringe-Driven-Development-Team/frontend#5`) → ничего;
- ошибка `gh` на одной из двух задач → вторая закрыта, `::error::` с номером первой, код ≠ 0;
- PAT пуст → `::error::`, код ≠ 0, запросов нет.

Условия запуска (не мерж, не ветка по умолчанию) — в `if:` job; проверяются actionlint и ревью, не скриптом.

`tests/telegram.sh`: комментарий с `<!-- auto -->` к задаче → сообщения нет; без маркера — как раньше. Плюс прогон `tests/lint.sh`, `tests/reminders.sh`, `tests/sprint.sh` — все зелёные (на Windows — таймаут 10 минут).

## Раскатка

Каждый шаг виден людям — перед каждым подтверждение пользователя.

1. Создать `frontend` и `backend` (`automation.yml`, README). Сразу за ним — шаг 2: до мержа `REPOS` утренняя проверка может сообщить о неподключённых репозиториях.
2. PR в `.github` с изменениями выше; мерж после зелёных тестов. До мержа — YarikMix проверяет права `ADD_TO_PROJECT_PAT` на задачи.
3. **Проверка.** Тестовая задача в `frontend` — с доски через `#` (подставился ли `Sprint`). Тестовый PR в личном репозитории пользователя с `Closes Cringe-Driven-Development-Team/frontend#N`: связь в `Development`, переход карточки в `In review`, «Create a branch for this issue» с выбором репозитория другой организации, закрытие после мержа. Затем тестовая задача закрывается как `not_planned` и убирается с доски, личный репозиторий удаляется. Страховку этот тест не задевает (в личном репозитории нет `automation.yml`) — её проверяет первый настоящий мерж в курсовом репозитории.
4. Сообщение команде в чат; перенос: dry-run → таблица пользователю → перенос.
5. PR в README frontend и backend с учётом результатов шага 3.
6. После согласования с менторами — выключить Issues в курсовых репозиториях.
