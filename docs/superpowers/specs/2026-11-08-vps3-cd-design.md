# Независимый CI/CD сервисов VPS3

## Цель и согласованные решения

GitHubBot и webhook-alerts автоматически выкатываются после успешного CI и публикации своего образа из main репозитория `.github`. Пользователь выбрал независимые выпуски: обновление одного сервиса не требует выпуска или перезапуска другого. Коммит digest в infra для каждого выпуска больше не нужен.

Обычные изменения инфраструктуры сохраняют выбранные версии приложений. CD проверяет VPS3 самостоятельно и не зависит от внешней проверки BFF/Go. Общие проверки infra сохраняются.

## Подходы

1. Независимые выпуски каждого сервиса после его CI — выбран пользователем. Позволяет выпускать и проверять сервисы отдельно.
2. Единый выпуск обоих образов одного коммита — отклонён: неудача одного сервиса задерживает второй и связывает независимые изменения.

## Текущее состояние

Оба publisher workflow живут в `.github`. GitHubBot publisher уже выполняет тесты, typecheck и image smoke; webhook-alerts publisher пока только собирает/публикует. Образы сейчас выбирает роль hooks из фиксированных переменных inventory/defaults. auxiliary.yml применяет общий Compose-проект `/opt/hooks`, содержащий приложения, Caddy и Telegram proxy. Основной infra apply заново рендерит Compose и может вернуть старый digest.

В infra уже настроен environment production с SSH/Vault и очередь infra-production. В `.github` production environment пока нет. Репозитории различаются, поэтому одинаковые имена concurrency group в двух репозиториях не обеспечат общую очередь.

## Предлагаемая архитектура (решение реализации)

Исполнитель выкладки находится в infra: отдельный workflow_dispatch workflow и отдельный Ansible playbook для сервисов VPS3. После успешного CI/publish сервисный CD из `.github` передаёт service, полный image_ref по digest, полный source_sha и request_id. Токен вызова имеет доступ только к запуску/чтению Actions нужного infra repo; SSH и Vault остаются в infra production.

Выкладка использует ту же concurrency group infra-production и не отменяет уже выполняющееся применение. Для очереди явно включается накопление ожидающих запусков, чтобы новый запрос не отменял уже ожидающий выпуск другого сервиса. Это последовательно выполняет оба CD и общий infra apply в одном репозитории. Пока очередь занята, CD ожидает свой запуск. Dispatch не считается успешной выкладкой: вызывающая сторона находит запуск по request_id, ожидает его завершения с ограниченным timeout и отражает фактический результат в CI.

Перед изменением VPS проверяются allowlist service/repository, формат digest/SHA, соответствие source-tag и manifest digest, успешная доверенная публикация из main `.github`, доступность публичного образа и его OCI source. Произвольный image, fork/PR и несовпадающие source/digest отклоняются. Код из произвольного ref не исполняется с production secrets.

## Образы и сохранение выбранных версий

На VPS сохраняются выбранные image_ref и source_sha отдельно для двух приложений. Формат и путь состояния определяет план, не смешивая его с секретами или SQLite. Обычный infra apply читает это состояние и сохраняет версии; CD меняет только выбранный сервис. Никакого latest и автоматического возврата к закреплённому inventory digest.

При переходе один раз импортируются фактически развёрнутые версии, сверенные с нынешними Compose, source-tag и публикациями. Несовпадение останавливает переход, а не угадывается. Статические application pins удаляются после подготовки состояния в рамках этой же реализации; это не постоянный legacy-режим.

Для первой установки на пустой VPS нужны явно переданные проверенные версии обоих сервисов. Отсутствующие или некорректные значения приводят к понятной ошибке, а не к молчаливому отключению GitHubBot. Обновление существующей VPS сохраняет оба тома SQLite и общие сети/настройки.

Запоздавший CD не должен заменить более новую выбранную версию того же сервиса. План закрепляет проверку порядка исходных коммитов относительно сохранённой версии. Повтор одного выпуска использует тот же опубликованный digest. Автоматический откат при ошибке не входит в задачу: CI сообщает ошибку и фактическое состояние; повтор запускает ту же проверенную версию.

## Границы операции выкладки

Deployment playbook не выполняет bootstrap, firewall/users, Pulumi или выкладку BFF/Go. Он валидирует существующую конфигурацию, загружает образ, готовит нужный сервис и запускает только его с необходимыми существующими зависимостями. Общий Compose сохраняется согласованным, соседний сервис остаётся на прежнем digest.

После запуска: точный image_ref работающего контейнера совпадает с выбранным; контейнер единственный, running и healthy. Для webhook-alerts дополнительно проверяется существующий HTTP health endpoint. GitHubBot проверяется без ручного getUpdates и без второго polling-процесса. Реальные сообщения в Telegram и изменения рабочих issues не требуются для CD.

Обновлённый release state не должен сообщать об успешной выкладке до health-проверки. При частичном сбое CI различает ошибку применения и успешный результат; следующий infra apply не должен молча выбрать другой образ. Конкретную последовательность записи desired/confirmed состояния и восстановление после сбоя закрепляет план.

## CI сервисов

Каждый сервис имеет собственный обязательный gate до публикации и dispatch: тесты, typecheck, сборка и smoke-проверка своего образа. Общие файлы включаются в зависимость обоих сервисов, когда они реально используются обоими. Изменения только GitHubBot не инициируют лишнюю выкладку webhook-alerts и наоборот. Отдельные workflow для PR проверяют код без публикации/production credentials.

Повтор publisher не переписывает уже опубликованный source-SHA tag другим образом; существующий manifest проверяется и возвращается как результат. Передача digest — через outputs/проверенный артефакт CI, без парсинга человекочитаемых логов.

## Credentials и эксплуатация

Нужен отдельный закрытый источник токена Actions для dispatch из `.github` в infra; имеющийся runtime GitHubBot PAT для Issues/Projects не используется. На момент исследования нужного секрета среди доступных repo/org metadata нет. Значение не публикуется в чате, коде или логах. Настройка секрета и проверка фактических permissions — обязательная часть приёмки, не заглушка.

Успех виден по двум job: публикация и подтверждённая выкладка. В итоговом отчёте — service, source SHA, image digest и ссылка на deployment run. Автоматические новые Telegram-уведомления отдельно не добавляются.

## Проверки и приёмка

- Успешное изменение GitHubBot автоматически меняет только его контейнер; аналогично webhook-alerts.
- Неуспешные тесты/сборка/manifest-проверка не допускают выкладку.
- Изменение только документации не вызывает лишней выкладки приложений; общая runtime-зависимость проверяется для затронутых сервисов.
- Повтор, устаревший выпуск и конкурирующие запросы не возвращают старую версию и не теряют версию соседа.
- Обычный infra apply после CD сохраняет обе выбранные версии.
- Ошибки dispatch, credentials, pull, проверки конфигурации и health делают CD красным; dispatch204 сам по себе не является успехом.
- Постоянные SQLite и один polling-процесс GitHubBot сохраняются.
- Обязательные проверки GitHubBot остаются обязательными. Общая ошибка BFF не маскируется и не определяет результат отдельного CD VPS3.
- Настоящая проверенная CI/CD выкладка каждого сервиса завершает приёмку.

## Не входит

Автоматизация сторонних образов Caddy/Xray, изменение приложения/команд/формата спринта, ремонт бэкенда, ротация runtime-токенов, новые уведомления, автоматический откат и требования безостановочной работы.
