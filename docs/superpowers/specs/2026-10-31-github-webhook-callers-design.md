# Завершение переключения GitHub-алертов на webhook

## Цель и границы

Убрать одновременную отправку событий GitHub через Actions и уже работающий
webhook worker для `docs`, `frontend-packages`, `figma`, `static`. Использовать
существующую organization variable `TELEGRAM_EVENTS_SOURCE=webhook` с
`visibility=selected`. Способ выполнения выбран владельцем: SDD. Необязательные
вопросы пропускаются по его просьбе.

Код отправителей, формат карточек, Apidog, board/close, reminders, course-sync,
release/deploy notifications не меняются. Worker остаётся включённым;
рабочая очередь не редактируется, старые сообщения не воспроизводятся и не удаляются.

## Подход

Расширение selected repositories — мой выбор на основе существующего контракта
и поручения завершить миграцию: добавить ровно четыре недостающих caller,
сохранив предыдущие четыре и любые обоснованные параллельные изменения.
`visibility=all` охватила бы также репозитории без caller и будущие репозитории;
изменять caller/workflow или удалять старый sender для этого переключения
не требуется. Дополнительных компонентов и зависимостей нет.

## Переключение и проверка

Перед изменением повторно прочитать настройки, очередь и выполняющиеся Actions
четырёх репозиториев. Дождаться уже запущенных notify, включая серии ревью,
не отменяя jobs. Зафиксировать UTC, GUID, SHA, ссылки jobs, message IDs.
Если появятся неразобранные сообщения на границе, сверить их по отдельности;
не менять очередь и не выключать общий worker ради этой миграции.

Добавить четыре repository ID штатным API добавления selected repository,
не заменять весь список. Проверить точный итоговый список и overrides.

В каждом из четырёх репозиториев создать временную ветку от актуального main,
затем push одного пустого коммита. Это настоящий GitHub push без изменения файлов
и main. Дождаться automation run: `telegram / notify=skipped`, другие jobs
сохраняют свои обычные условия. Сопоставить событие по repo/ref/after SHA/GUID с
HTTP 202 и единственным `sent` outbox, topic 26 и Telegram message ID. Проверить
отсутствие второй delivery с тем же событием/SHA и единственность outbox после
завершения Actions и worker. Удалить только свои временные ветки после сверки;
событие удаления не должно создавать сообщение.

Независимые workflow сверить по неизменности файлов и существующим проверкам;
не запускать deploy/release ради проверки уведомлений. Проверку новой issue/PR
использовать только если push не позволяет подтвердить реальную доставку.

## Результат и ограничения

Сохранить фактический журнал в `services/webhook-alerts/README.md`: до/после,
граница старых jobs, четыре live-проверки, GUID/run/job/message IDs, снимок
состояния очереди. Разделить порядок первого запуска и расширение охвата при
уже включённом worker. Обновить устаревшее описание состояния/onboarding в
корневом `README.md`; настройки выбранных репозиториев проверяются при добавлении
каждого нового caller.

Проверки: существующие `tests/webhook-workflows.test.ts`, `tests/telegram.sh`,
`tests/reminders.sh`, `tests/close.sh`, `tests/lint.sh`; настоящие события для всех
четырёх новых caller. Новая логика приложения и новые тестовые абстракции не нужны.
Результат — ветка и reviewable PR в `.github`, отдельная задача по правилам CDD.
Мерж PR выполняется при отдельном поручении владельца; переключение variable
входит в текущее поручение.

GitHub delivery deduplication не обеспечивает абсолютную exactly-once доставку
при потере ответа Telegram после отправки. Здесь проверяется отсутствие двух
отправителей и ровно один подтверждённый результат для контрольного события.
Исторические дубли в чате остаются; конфигурационное переключение их не удаляет.
