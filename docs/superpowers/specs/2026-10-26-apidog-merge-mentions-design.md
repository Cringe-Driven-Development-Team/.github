# Упоминания участников и две кнопки в алерте о мерже Apidog

## Зачем

После слияния sprint-ветки Apidog уже присылает событие `BRANCH_MERGED` в тему
Apidog общего Telegram-чата. В нём есть имя ветки и сводка изменений, но нет
персональных упоминаний и кнопок на конкретный Merge Request и опубликованный
контракт. Создатель MR и человек, который его слил, должны получить уведомление
в этой теме и открыть нужный ресурс одним нажатием.

Пример, подтверждённый владельцем и чтением сохранённой доставки: проект
`1382426`, целевая ветка `main` (`1388508`), MR `39834`, создатель
Валентин Кунев (`createdById=1066826`),
слил Александр Батовкин (`closedById=1067537`). Прямая ссылка из Apidog:
`https://app.apidog.com/project/1382426/branch/1388508/merge-request/39834`.
Командный справочник связывает их с GitHub-логинами `MrDuckVC` и
`blackHATred`; оба логина уже есть в существующей карте Telegram пользователей
организации.

У настоящей доставки `BRANCH_MERGED` есть только строковые ключи `event`,
`title`, `content`; `appLink` отсутствует. В `content` отдельными строками
пришли `Merge Sprint Branch: <имя>`, `Project: <имя>`,
`Updated at: 2026-10-26 10:28:47`. Для этого MR значение `Updated at`
совпало до секунды с `closedAt=2026-10-26T10:28:47.000Z`, полученным через
Apidog CLI. Значит, для наблюдаемого формата время в содержимом — UTC, с
точностью до секунды. При другом или неполном формате не угадывать часовой
пояс или MR.

## Поведение

- Только для подписанного события `BRANCH_MERGED` сервис в фоне, после записи
  доставки в SQLite, находит соответствующий **слитый** MR в том же проекте,
  из той же исходной ветки в `main`. Он сопоставляет время `Updated at` из
  события с `closedAt` MR до секунды; при нескольких кандидатах не угадывает,
  кому отправлять пинг.
- В прежний топик Apidog отправляется одно сообщение с исходной сводкой,
  строками `Создатель MR: <упоминание Валентина>` и
  `Слил MR: <упоминание Александра>` и двумя кнопками в одной строке:
  `Открыть MR` на точную ссылку и `Контракт API` на
  `https://vb78fyael1.apidog.io/`.
  Это упоминания в групповом топике, без личных сообщений. Когда один человек
  выполняет обе роли, в тексте остаются обе роли, но повторный пинг не нужен.
- Telegram-упоминание строится по числовому Telegram ID как HTML-ссылка
  `tg://user?id=...`; имя в ссылке берётся из проверенной карты участников.
  Нельзя определять человека по тексту `Updated By` или угадывать его по
  имени ветки. Для неизвестного Apidog ID роль остаётся читаемой без пинга.
- Если Apidog недоступен, ответ неоднозначен или MR не найден, исходный алерт
  всё равно отправляется без вымышленных упоминаний и ссылки на MR, но с
  кнопкой `Контракт API`. Ошибка фиксируется только безопасным кодом; payload,
  токен и ответ Apidog не пишутся в журнал. Для остальных событий Apidog
  формат остаётся прежним.

Пример вида сообщения (имена служат текстом ссылок, IDs не показываются):

```text
Apidog · BRANCH_MERGED
Merge Sprint Branch Into Master
Merge Sprint Branch: ai/20261025-from-main-api41-review
...
Создатель MR: Валентин Кунев
Слил MR: Александр Батовкин
[Открыть MR] [Контракт API]
```

## Получение данных и настройка

Нынешний webhook форматтер читает только `event`, `title`, `content`,
`appLink`. В настоящем merge-событии нет `appLink`; один лишь текст события не
содержит ID MR или его создателя. Поэтому обогащение выполняет worker через доступный
для чтения Apidog Merge Request interface. [Официальная CLI](https://docs.apidog.com/609656m0) поддерживает
`merge-request list --from ... --status MERGED` и `merge-request get`; эти
операции уже проверены для MR `39834`. В реальном вызове `--from` вернул и
чужие MR, поэтому сервис дополнительно сверяет числовые `sourceBranchId`,
`targetBranchId` и `closedAt` каждого кандидата и обходит страницы результата;
одного серверного фильтра недостаточно. Реализация может использовать CLI или
эквивалентные запросы чтения, если сохраняет тот же проверенный контракт.
Сетевые запросы ограничиваются по времени. Приём webhook не ждёт Apidog.

Проект, целевая ветка и публичный URL контракта заданы конфигурацией сервиса.
URL `https://vb78fyael1.apidog.io/` проверен: он отдаёт HTTP 200. Сервис
сохраняет обе кнопки в очереди до отправки и формирует из них одну строку
Telegram inline keyboard. Нынешние одиночные кнопки GitHub-алертов сохраняют
своё поведение. Шаблон прямой ссылки собирается из валидированных числовых
`projectId`, `targetBranchId` и `MR id`,
а не из произвольной ссылки webhook. Если Apidog всё же прислал `appLink` для
другого типа события, нынешнее поведение не меняется.

На VPS потребуется `APIDOG_ACCESS_TOKEN` с доступом к MR проекта, только в
`vault_hooks_env`. Карта `Apidog user ID → отображаемое имя, Telegram user ID`
также поступает из Vault; начальные Telegram ID берутся из уже настроенной
карты организации, без публикации их в репозитории. Для новых участников
карту дополняют. Токен не передаётся в командной строке, URL или логах.

## Границы и проверка

Не меняем выбор событий в Apidog, GitHub-алерты, схему webhook и способ
доставки Telegram. Не уведомляем всех назначенных reviewers: нужный человек
определяется по `closedById`, второй — по `createdById`. Не используем ложную
ссылку на список MR как кнопку `Открыть MR`.

Проверить локально однозначный MR, отсутствие MR, несколько кандидатов,
неизвестного участника, недоступный Apidog, небезопасные поля webhook и
отсутствие утечки токена. Отдельно проверить точную ссылку `39834` и
Telegram-карточку в тестовом чате/топике. После развёртывания проверить
следующий настоящий merge; для текущего MR не создавать новую публикацию в
боевом чате.

Планировщик выбирает конкретный модуль Apidog-клиента, формат настройки и
порядок локальных проверок; он не меняет описанное поведение без согласования.
