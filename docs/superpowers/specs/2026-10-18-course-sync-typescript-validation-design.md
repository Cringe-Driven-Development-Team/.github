# Проверка CI перед синхронизацией учебных репозиториев на TypeScript

Дата: 2026-10-18
Статус: на ревью пользователя; реализация не начата.

## Цель и границы

Перенести проверку GitHub API из `scripts/course-sync-context.sh` в TypeScript, чтобы отказ синхронизации называл конкретную причину и не возникал из-за одного временно несогласованного ответа API. Сохраняются требования безопасности: учебный `main` получает только коммит принятого `main` frontend/backend после успешных обязательных проверок его push CI. Операции с Git, SSH-ключом и временными файлами остаются в Bash. Уведомления об ошибке и восстановлении пока остаются в существующих Bash-скриптах.

В двух известных запусках — frontend `39082862392` и backend `39162316999` — первый sync остановился до копирования на общей проверке provenance, а повтор той же проверки позднее прошёл. Логи не содержат ответа API, поэтому конкретное несовпавшее поле неизвестно. Дизайн исправляет непрозрачность ошибки и допускает ограниченный повтор чтения; он не объявляет установленной причиной какое-либо одно поле или поведение GitHub.

## Выбранный подход

Исходники новой проверки — TypeScript в репозитории `.github`. При разработке и проверке они компилируются средствами Node/npm; исполняемый JavaScript коммитится вместе с исходниками. В GitHub Actions он запускается как локальное JavaScript action с `runs.using: node24` после checkout **того же закреплённого коммита** `.github`, который указан в `automation_ref` caller workflow. В sync-job не устанавливаются Bun, npm-пакеты или компилятор; его зависимость во время выполнения — встроенный Node 24 и GitHub REST API.

Рассмотрены также запуск TypeScript через `setup-bun` в каждом sync-job и сохранение Bash с расширенной диагностикой. Bun согласуется со стеком будущего сервиса вебхуков, но добавляет установку рантайма в критический путь синхронизации. Bash-правка меньше по объёму, однако оставляет многоступенчатый разбор JSON и проверки нескольких ответов в shell. Выбранный вариант ограничивает новый стек одной проверкой и позволяет отдельно тестировать логику ответов API. Сервис вебхуков и эта автоматика не обязаны иметь одинаковый рантайм.

## Компоненты и поток данных

1. `sync-to-course.yml` сохраняет начальную проверку caller-контекста и checkout `.github` по полному `automation_ref`. Шаг `Verify CI provenance and required jobs` вызывает локальное Node action из checkout `automation/`, передавая `SOURCE_REPO`, `CI_RUN_ID`, `SHA` и временный `GITHUB_TOKEN` с нынешними правами `actions: read`, `contents: read`.
2. Action проверяет формат входов и фиксированную карту назначений: командный frontend → учебный frontend, командный backend → учебный backend. Другие репозитории или произвольный target не принимаются.
3. Через GitHub REST API action читает CI run, определение workflow `.github/workflows/ci.yml` и все страницы jobs нужных попыток. Он требует push в `main` указанного репозитория с точным SHA и правильным workflow ID. Для frontend обязателен успешный `Check`, для backend — `lint`, `test`, `docker`. При job-only rerun используется результат последней попытки каждого обязательного job; неоднозначность, пропуск или ошибка обязательного job дают отказ.
4. После чтения jobs action повторно читает CI run и сверяет идентичность запуска и номер попытки. Только после успешной проверки он записывает фиксированный `target` в output `context.target`. Ни ответ API, ни входной target не становятся командой shell.
5. Следующий шаг без изменения текущего интерфейса использует output и запускает существующий `scripts/course-sync-git.sh`. Проверки fast-forward, запрет force push, SSH host key, очистка ключа и логика уведомлений остаются на своих местах.

## Отказы и временно несогласованные ответы

При каждом отказе action пишет имя условия и безопасные ожидаемое/полученное значения для полей run/workflow: ID, event, branch, SHA, repository, head repository, status, attempt, workflow ID/path. Токен и полный JSON-ответ не печатаются. Ошибки HTTP, неполная пагинация и неверные статусы jobs получают отдельные сообщения.

Для чтения метаданных run/workflow и полного списка jobs допускается ограниченный повтор при несоответствии или неполном ответе: не более 60 секунд суммарно, с паузой до 5 секунд между попытками и таймаутом каждого HTTP-запроса не более 10 секунд. Каждая попытка заново проверяет все условия; запись в учебный репозиторий до полного успеха невозможна. Неверный формат входов отклоняется сразу без запроса API, а завершившийся неуспешно обязательный job даёт отказ без ожидания. Если после срока несоответствие остаётся, action завершается ошибкой с последним конкретным условием. Успех не выводится из одного лишь прошедшего времени или из успешности других jobs.

Повтор валидации не заменяет повторное чтение CI run после проверки jobs. Если номер попытки или идентичность запуска меняется во время проверки, текущая попытка валидации отбрасывается и начинается заново в пределах того же срока. Если обязательный job завершён неуспешно, синхронизация отказывается от данного снимка; будущая успешная попытка CI может быть обработана отдельным job-only rerun или ручным workflow, как сейчас.

## Проверки и выпуск

В `.github` добавляются Node/npm manifest и lockfile только для сборки и тестов нового action. Проверки должны подтверждать, что закоммиченный JavaScript соответствует TypeScript-исходнику, без установки зависимостей во время sync. Тесты на фикстурах покрывают правильный frontend/backend run, каждый неверный provenance-параметр, все страницы jobs, job-only rerun, изменение attempt при чтении, первый неполный/несогласованный ответ с последующим валидным, исчерпание срока и отсутствие output при отказе. Существующие тесты `course-sync-git.sh` и workflow lint продолжают проходить. Отдельная проверка workflow подтверждает путь локального action и сохранение прав и входов reusable workflow.

Порядок выпуска: сначала PR в `.github` с action, собранным JavaScript и обновлённым reusable workflow; старые callers продолжают ссылаться на прежний SHA. После проверки и слияния обновляются **оба** caller-репозитория: `uses` и `automation_ref` получают один и тот же полный новый SHA `.github` в CI и ручном sync workflow. До обновления caller новое поведение не включено. Для каждого caller проверяются PR CI, затем первый push/main sync и равенство SHA командного и учебного `main`. Frontend и backend можно переключать последовательно; сбой одного не меняет другой.

## Критерии приёмки

- На известном валидном CI run новая проверка возвращает тот же фиксированный target; на неверном run или неуспешных обязательных jobs не возвращает target и не запускает Git-шаг.
- Отказ provenance называет конкретное поле. Временный неверный ответ может смениться валидным в пределах 60 секунд; постоянный отказ остаётся красным с понятной причиной.
- Runtime sync-job не требует Bun или установки npm-пакетов, а сборка воспроизводится из lockfile и проверяет актуальность коммитнутого JavaScript.
- После переключения frontend и backend штатный sync проходит; учебные `main` совпадают с соответствующими командными SHA. Deploy и upload не повторяются ради проверки или восстановления sync.

За пределами изменения: перенос Git/SSH и Telegram-уведомлений на TypeScript, переработка release/deploy, изменение карты учебных репозиториев, отключение защит provenance или расширение прав `GITHUB_TOKEN`.
