# Apidog: только уведомления о MR

## Задача

Тема Apidog в Telegram должна получать только открытие, закрытие и слияние merge request. Уведомления об изменениях API, схем, документов и о создании веток создают шум. Уже отправленные сообщения не меняются.

## Источник событий

Apidog Notification Events предоставляет `Sprint Branch Merged`, но не события открытия или закрытия MR. Поэтому сервис получает состояние MR через авторизованный read-only API, который уже используется для обогащения сообщений. Опрашиваем все страницы списка MR целевой ветки `main` раз в 30 секунд. Список содержит ID, статус `OPEN | CLOSED | MERGED`, автора, участников, описание и время создания/закрытия. Webhook от Apidog продолжаем проверять и принимать, но не создаём из него Telegram-сообщения. Единый источник трёх MR-событий исключает дубли между webhook и опросом.

## Граница истории и доставка

При первом запуске новой версии фиксируем время старта в SQLite до сетевого запроса. MR, созданные раньше этой границы, считаются уже открытыми; их старое открытие не отправляем. Если такой MR закрыт или влит после границы, отправляем соответствующее уведомление. Для нового MR, успевшего открыться и закрыться между опросами, ставим в очередь оба события в хронологическом порядке.

События имеют постоянные ID `mr-poll:<MR ID>:<OPENED|CLOSED|MERGED>` в существующей таблице `deliveries`. Исторические события помечаются подготовленными без outbox, новые остаются в очереди worker. Вставка всей страницы состояния и границы выполняется транзакционно; рестарт и повторный опрос не повторяют уведомления. Ошибка API не меняет состояние; следующий цикл повторяет запрос. Неполный или неоднозначный ответ не обрабатываем частично.

## Карточка

Для каждого события отправляем название действия, номер MR, краткое описание, автора и того, кто закрыл/слил MR, если применимо. Упоминания берём из существующей карты Apidog → Telegram; неизвестный пользователь виден без пинга. Кнопки ведут на конкретный MR и опубликованный контракт API. Поля API экранируем как недоверенный текст. GitHub-алерты и их очередь не меняем.

## Проверка

Тесты: начальная граница без исторического спама, новый OPEN, OPEN → CLOSED, OPEN → MERGED, открытие и завершение между опросами, рестарт/повторный опрос, сбой/неполная пагинация, отсутствие Telegram для `API_UPDATED` и `BRANCH_CREATED`, безопасное форматирование. После выкладки проверить digest, health, успешный первый опрос без массовых сообщений; реальное новое MR-событие проверить при следующем MR.

## Ограничение

Уведомления приходят с задержкой до 30 секунд плюс время ответа API. Apidog не документирует webhook для открытия и закрытия MR; опрос — выбранный источник этих событий. Повторное открытие того же ID после закрытия не предусмотрено текущим процессом Apidog: отклонённый MR создают заново.
