# Как работать с задачами

Как завести и закрыть задачу в репозиториях организации — для менторов и для команды. Задачи видны на доске [Scrumban](https://github.com/orgs/Cringe-Driven-Development-Team/projects/1).

Ветки, коммиты и ревью описаны в README репозитория с кодом: [frontend](https://github.com/frontend-park-mail-ru/2026_2_Cringe_Driven_Development#как-работать-с-задачами), [backend](https://github.com/go-park-mail-ru/2026_2_Cringe_Driven_Development#как-работать-с-задачами).

## Где живёт задача

Задачи заводятся только в репозиториях организации. У фронта и бэка код лежит в курсовых репозиториях, но задачи там не заводим: их не увидят доска, бот и смена спринта. Для задач в организации есть отдельные репозитории без кода — [frontend](https://github.com/Cringe-Driven-Development-Team/frontend) и [backend](https://github.com/Cringe-Driven-Development-Team/backend).

Репозиторий выбирается по области. Если задача затрагивает несколько областей — по той, куда придётся основная часть работы. Заголовок — `<Область>. <Что сделать>`, например `DevOps. Приватный бакет для ноутбуков`.

| Область | Где заводить задачу | Где код |
|---|---|---|
| `Frontend.`, `BFF.` | [frontend](https://github.com/Cringe-Driven-Development-Team/frontend) | курсовой — [frontend-park-mail-ru/2026_2_Cringe_Driven_Development](https://github.com/frontend-park-mail-ru/2026_2_Cringe_Driven_Development) |
| `Backend.` | [backend](https://github.com/Cringe-Driven-Development-Team/backend) | курсовой — [go-park-mail-ru/2026_2_Cringe_Driven_Development](https://github.com/go-park-mail-ru/2026_2_Cringe_Driven_Development) |
| `DevOps.` | [infra](https://github.com/Cringe-Driven-Development-Team/infra) | там же |
| `React.` | [react](https://github.com/Cringe-Driven-Development-Team/react) | там же |
| `Figma.` | [figma](https://github.com/Cringe-Driven-Development-Team/figma) | — |

Префикс называет область, а не исполнителя: задачу `Frontend.` может делать девопс. Исполнитель — в `Assignees`.

## Как завести

На доске в нужной колонке: `+ Add item` → ввести `#` → выбрать репозиторий → `Create new issue`.

> [!WARNING]
> Текст без `#` создаёт черновик: он живёт только на доске, из него нельзя создать ветку, и pull request его не закроет.

## Описание

В `Backlog` задача может быть заготовкой с одним заголовком. В `Ready` — только с описанием: по нему исполнитель делает задачу, а ментор её принимает. Описание пишет тот, кто переводит задачу в `Ready`.

````markdown
## Цель

Что изменится, когда задача будет сделана, и зачем.

## Что сделать

- [ ] Шаг, который можно проверить.

## Приёмка

- Наблюдаемый результат: что открыть или запустить и что увидеть.

## Зависимости

1. Задачи и PR, без которых эту не сделать.

## Не входит

- Что рядом, но делается другой задачей.
````

«Цель», «Что сделать» и «Приёмка» обязательны. «Зависимости» и «Не входит» — когда есть что написать. Образец — [infra#20](https://github.com/Cringe-Driven-Development-Team/infra/issues/20).

## Задача на несколько репозиториев

Один PR закрывает одну задачу. Если работа затрагивает несколько репозиториев, PR у задачи несколько, и первый влитый закрыл бы её раньше времени. Поэтому задача делится:

1. Сама задача остаётся в репозитории той области, куда приходится основная работа. Это родитель.
2. На каждый другой репозиторий заводится sub-issue в нём: в родителе `Create sub-issue` → выбрать репозиторий. В неё переезжают пункты «Что сделать» и «Приёмки», которые относятся к этому репозиторию; в родителе остаётся ссылка.
3. PR в другом репозитории закрывает свою sub-issue. PR в репозитории родителя закрывает родителя и мержится последним.

Пример: [frontend#6](https://github.com/Cringe-Driven-Development-Team/frontend/issues/6) — выкатка клиента, родитель; [infra#22](https://github.com/Cringe-Driven-Development-Team/infra/issues/22) — правило в Caddy и CORS, sub-issue.

Бывает, что PR родителя нужно влить раньше остальных или своего PR у родителя нет. Тогда родителя закрывает ментор, когда закрыты все sub-issues, а в PR родителя стоит `Part of …`, не `Closes …`.

Правке в другом репозитории на пару строк sub-issue не нужна. В описании такого PR — `Part of Cringe-Driven-Development-Team/frontend#6`: ссылка появится под задачей, но не закроет её.

## Как закрыть

### Через pull request

В описании PR — строка с ключевым словом и номером задачи.

| Где PR | Строка |
|---|---|
| курсовой репозиторий фронта или бэка | `Closes Cringe-Driven-Development-Team/frontend#12` |
| тот же репозиторий, что и задача | `Closes #12` |

- В курсовом репозитории ссылка только полная: короткое `#12` сошлётся на сам курсовой репозиторий, и задача не закроется.
- Строка работает в описании PR. В описании задачи и в комментариях она ничего не закрывает.
- Задача закрывается при мерже в `main`, карточка уезжает в `Done`. Руками закрывать не нужно.
- PR, который делает только часть задачи, пишет `Part of …` вместо `Closes …`.

PR курсовых репозиториев мержат менторы без прав на организацию — задачу за них закрывает автоматика, подробности в [README](README.md#задачи-фронта-и-бэка).

### Без pull request

Макеты, домашние задания, ручная настройка — у таких задач PR нет.

1. Исполнитель оставляет под задачей комментарий со ссылкой на результат и переводит карточку в `In review`.
2. Ментор направления проверяет по «Приёмке» и закрывает задачу. Не принял — пишет под задачей, что доделать, и возвращает карточку в `In progress`.

### Задача больше не нужна

`Close as not planned` и комментарий, почему.
